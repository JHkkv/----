# 确认门机制（Gate Mechanism）

> 本 Skill 最核心的设计。对应需求："实操之前必须出示具体方案，同时方案需要你提出问题，商家回答在合理范围之内你才能去进行下一步的执行，否则你可以直接拒绝执行。"
>
> **不可违背的红线**：GATE-1（草案+提问）和 GATE-2（回答审查）在任何模式下不可跳过。不允许谄媚迁就使用者。

## 一、确认门总览

| 门 | 位置 | 强制 | 核心行为 |
|----|------|------|---------|
| 权限询问 | P0 | 默认 | 展示权限清单，收授权 |
| 确认点A-E | P2/P3/P6/P7/P8 | 可跳过 | 展示阶段产出，收确认 |
| **GATE-1** | **P4** | **强制** | 出示方案草案 + 向商家提问，**必须全部回答** |
| **GATE-2** | **P5** | **强制** | 审查商家回答合理性，不合理则**拒绝执行** |

## 二、GATE-1：方案草案 + 商家提问

### 2.1 触发时机

P3 调研确认通过后，进入 P4。此时必须：
1. 综合诊断 + 调研 + 对标结果，形成**具体可执行的优化方案草案**
2. 从草案中提取 **5-8 个待验证假设**，转化为给商家的问题
3. **先展示完整草案，再逐题发问**

### 2.2 草案要求（必须让商家"切实了解"方案）

| 必须包含 | 要求 |
|---------|------|
| 诊断结论摘要 | TOP3 核心问题，说明数据依据 |
| 对标结论 | 对标了哪些爆品/榜单前十、学到什么、差距在哪 |
| 优化动作 | 分模块列出（页面/投流/内容/活动），每个动作说清"做什么、为什么、怎么做" |
| 预期收益 | 标注可信度等级，**不承诺具体销量数字**（用"预期提升 X%-Y%，可信度 C 级，需 A/B 测试验证"） |
| 资源需求 | 时间 / 预算 / 人力 / 依赖 |
| 风险评估 | 方案的失败场景与备选 |

**禁止**：草案不展示就发问；草案过于笼统（如"优化主图"而无具体方向）。

### 2.3 问题设计要求

| 要求 | 说明 |
|------|------|
| 数量 | 5-8 题 |
| 对应关系 | 每题对应一个方案成立的关键假设（不是闲聊题） |
| 具体性 | 可量化回答（如"客单价是多少""成本结构如何"），不空泛 |
| 用途标注 | 每题标注"该答案将影响方案中 X 部分的可行性" |
| 类型 | 数据题（客单价/成本/库存/复购率）+ 意图题（目标人群/预算/接受改动程度）+ 资源题（人力/时间） |

**问题示例**（某收纳用品商家场景）：
1. 客单价和毛利结构大概是多少？→ 影响定价与活动机制设计
2. 转化率长期偏低，你觉得是产品问题还是展示问题？→ 影响诊断结论权重
3. 你愿意为页面改版投入多少预算？→ 影响改版方案深度
4. 主打人群是谁（价格敏感/品质优先/学生/宝妈）？→ 影响文案与视觉方向
5. 目前有无站外引流渠道（小红书/抖音）？→ 影响内容矩阵方案
6. 库存和供货周期如何？→ 影响活动与投流放量节奏
7. 你对"改主图/详情页"的接受程度（可接受大改/仅小改）？→ 影响改动幅度

### 2.4 发问方式

用 AskUserQuestion 逐题发问（或一次发多题）。等待全部回答后才进入 P5。

**快速模式例外处理**：即使用户说"跳过确认/快速模式"，GATE-1 不可跳过。应对话术：

> 这一步是整个方案的质量闸门——我需要先确认你理解了方案、并且方案成立的关键假设都有答案。这不是流程上的形式，而是为了不让你拿着一份跑偏的方案去执行。请逐题回答以下 N 个问题。

## 三、GATE-2：商家回答合理性审查

### 3.1 R1-R5 审查标准（核心判定逻辑）

| 编号 | 判定维度 | 不合理判定条件 | 严重等级 |
|------|---------|---------------|---------|
| **R1** | 答非所问 | 回答与问题无关，或回避核心问题 | 轻微 |
| **R2** | 明显敷衍 | 回答 <5 字；套话（"都挺好的""没什么问题"）；连续 ≥3 题同一措辞 | 轻微 |
| **R3** | 前后矛盾 | 不同问题的回答之间存在逻辑矛盾（如 P1 月销 100 单但 P4 转化率 5% 而访客仅 500 → 5%×500=25 单≠100 单） | **严重** |
| **R4** | 提供虚假数据 | 明显夸大或与公开可查数据严重不符（如声称类目第一但平台公开榜单未见其名） | **严重** |
| **R5** | 拒绝关键信息 | 核心执行依赖的信息商家拒绝提供，且无法用替代方案绕过 | **严重** |

### 3.2 判定流程

```
商家回答
   │
   ▼
逐条对照 R1-R5
   │
   ├─ 全部通过 ────────────────→ ✅ 通过 → P6
   │
   ├─ 轻微问题（个别 R1/R2）───→ ⚠ 标注问题 → 要求重答 → 重答后通过 → P6
   │                            （重答仍敷衍 → 升级为严重）
   │
   └─ 严重问题（R3/R4/R5，或 ≥3 个轻微）→ 🚫 触发拒绝协议 → 流程终止
```

**判定细则**：
- 轻微问题重答次数上限：**1 次**。重答后仍不达标 → 升级为严重，触发拒绝协议。
- 严重问题不提供重答机会（R4 提供虚假数据尤其不可容忍）——直接触发拒绝协议。
- 连续两次独立审查轮次（跨会话或同一会话重来）都不通过 → 使用升级话术。

### 3.3 合理性审查报告模板

```markdown
## 合理性审查报告（GATE-2）

审查轮次：第 N 轮

### 逐题审查结果
| 问题 | 商家回答 | 判定 | 说明 |
|------|---------|------|------|
| Q1 客单价 | ¥89 | ✅ 通过 | 与 P1 提供数据一致 |
| Q2 转化率低的原因 | "我觉得是展示问题" | ✅ 通过 | 有明确倾向，可验证 |
| ... | ... | ... | ... |

### 数据交叉核验
- [ ] 与 P1 商家档案一致
- [ ] 与公开可查数据不冲突
- [ ] 无内部矛盾

### 最终判定
- [ ] ✅ 通过 → 进入 P6
- [ ] 🚫 拒绝执行 → 触发拒绝协议（原因：R3/R4/R5...）
```

## 四、拒绝协议

### 4.1 触发条件

GATE-2 判定为严重问题（R3/R4/R5，或重答后仍敷衍）。

### 4.2 标准版拒绝话术

```
【标准版】

感谢你的回答。我对你提供的信息做了交叉核验。

以下 [N] 个问题未能通过合理性审查：
1. [具体问题] — [不通过原因，引用具体 R1-R5 标准]
2. ...

在目前的信息基础上继续往下执行，会产生不可靠的方案——这对你的经营决策没有帮助。
所以我需要暂停当前流程。

你可以选择：
- 重新回答上述问题，确保信息准确、完整；
- 如果确实无法提供某些信息，告诉我"无法提供"，我会标记该数据依赖为"商家未提供（可信度：待补充）"，并调整方案范围；
- 如果不想继续，回复"结束"即可。

我不会为了推进流程而接受不合理的回答——这是一个原则问题。等你准备好后，我们再继续。
```

### 4.3 简短版话术（问题单一明确时）

```
【简短版】

[具体问题]的回答与之前提供的信息存在矛盾（[简述矛盾点，如"月销100单与转化率数据对不上"]）。
在澄清这个矛盾之前，我无法继续。请重新确认。
```

### 4.4 升级版话术（连续 2 次审查不通过后）

```
【升级版】

这是第二次审查不通过了。坦白讲，如果关键信息无法对齐，我做出的方案反而可能误导你的决策。
我不建议在信息不足的情况下继续推进。

如果你愿意，我们可以缩小范围——只做不依赖这些数据的部分（比如竞品对标 + 内容优化），
跳过后台数据依赖的模块。这样至少能给你一些真正有用的东西。
```

### 4.5 拒绝后的选项路径

| 商家选择 | 处理 |
|---------|------|
| 重新回答 | 回到 P4 重答（计 1 次审查轮次），重答后重新审查 |
| 缩小范围 | 只执行不依赖被拒数据的模块，标记数据缺口，继续 P6 |
| 结束 | 流程终止，输出已产出内容（含拒绝记录） |
| 不回应 | 流程挂起，等商家回应 |

### 4.6 拒绝记录（入档）

每次拒绝都要记录到确认门记录表 + 归档（脱敏）：
- 被拒的问题、商家回答、判定标准（R几）、拒绝话术版本
- **自学习价值**：这些"商家拒绝模式"是 Skill 学习的重要素材（哪些问题商家不愿意答、哪些数据商家拿不出）

## 五、与其他机制的关系

- **与快速模式**：快速模式只跳过确认点 A-E，GATE-1/GATE-2 不可跳过（见 phase-transitions.md）。
- **与数据可信度**：商家拒绝提供的数据，相关结论降级为 C 级领域推理，并附加强制提示。
- **与归档**：GATE 结果（通过/拒绝）入档，脱敏后用于自学习。
- **免责声明**：所有涉及预期收益、建议的表述，末尾附统一免责声明（见 agent-profiles.md 的 DISCLAIMER-AGENT）。
