# Dify DSL 生成过程复盘

> 罗南杨 · 2026-07-22

## 一、发生了什么

用户需求：生成一个"用户提供想法 → DeepSeek 优化提示词 → 千问生人物图 → DeepSeek 优化分镜 → 千问输出视频"的 Dify 工作流 DSL 文件。

结果：文件生成后**两次导入失败**——第一次导入报"应用创建错误"，第二次运行时报"Variable #sys.query# not found"——共花了 3 轮诊断修复才通过。教学教程方面，用户反馈内容对小白不够友好、实操性不足。

## 二、DSL 生成：问题与教训

### 错误 1：环境变量 value_type 不对

| 我写的 | Dify 实际格式 |
|--------|-------------|
| `value_type: number` | `value_type: integer` |

**根因**：没有逐字段对照官方测试 DSL（`api/tests/fixtures/workflow/`），凭经验写了 `number`，但 Dify 反序列化期望的是 `integer`。

**教训**：生成 DSL 之前，应该**先提取一份官方 DSL 做字段 schema 对照表**，逐个字段确认类型名，而不是凭记忆写。

### 错误 2：Workflow 模式引用了 Chat 模式的变量

```yaml
# ❌ workflow 模式没有 sys.query 这个变量
memory:
  query_prompt_template: '{{#sys.query#}}...{{#sys.files#}}'
```

**根因**：`sys.query` 只在 `advanced-chat` 模式下可用。所有官方测试 DSL 里，workflow 模式的 `query_prompt_template` 都不引用 `sys.query`（只有 chatflow 模式才用）。我直接把 chatflow 模板的 memory 配置复制到了 workflow 模式。

**教训**：LLM 节点的 `memory.query_prompt_template` 即使 `window.enabled: false` 也会被 Dify 校验变量引用。在 workflow 模式下应该引用 Start 节点定义的变量（如 `{{#start-node.idea#}}`）或者留空字符串。

### 错误 3：YAML 中写了注释

YAML 虽然支持 `#` 注释，但某些严格的 YAML 反序列化器在处理注释后再做 round-trip 时可能出现意外行为。Dify 的 DSL 解析管线涉及 YAML → JSON → Pydantic 多层转换，注释对其不如纯数据可靠。

### 正确做法（以后）

生成 Dify DSL 文件的标准流程：

```
1. 读取 api/tests/fixtures/workflow/ 下同模式的官方 DSL 作为模板
2. 提取每个节点类型的 data 字段结构做对照
3. 逐字段对照官方值：mode/version/value_type/provider 格式/依赖项
4. 生成后跑校验：
   - YAML 语法校验（pyyaml safe_load）
   - 边完整性校验（source/target 必须在节点列表中）
   - 变量引用校验（无跨作用域引用、模式匹配）
5. 输出给用户前标注："导入后需要配置模型供应商的 API Key"
```

## 三、教学教程：内容层面的反思

### 问题诊断

这次教程存在三个层面的问题：

**1. 跳过了"入门门槛"**

概念篇一上来就讲源码路径 `api/core/workflow/workflow_entry.py`、Graphon 引擎、block_factory，这些对小白来说是噪音。一个刚接触 Dify 的用户不需要知道 `resolve_workflow_node_class` 函数签名。

**正确做法**：入门层应该完全屏蔽源码细节，纯讲"这是什么、能做什么、怎么拖第一个节点"。源码引用放在进阶篇或附录。

**2. 实操内容密度不够**

5 个实战案例看似很多，但每个案例只给了工作流结构图 + 配置表格，缺少：
- 手把手的屏幕截图式步骤（"点击左上角 + 号 → 选择 LLM 节点 → 在右侧面板填入..."）
- 每步的预期结果（"此时你应该看到..."）
- 调试技巧（"如果运行报错，检查这 3 项..."）

**3. 概念讲解太密集**

28 种节点在一次教程里全列出来，超出了初学者的吸收能力。应该分层：
- 入门：只讲 5 个核心节点（Start / LLM / Code / End / IF-ELSE）
- 进阶：再加 5 个（知识检索 / HTTP / 模板 / 分类器 / 迭代）
- 高级：余下的 18 个

### 核心原则

**教程不是源码注释，是路径指引。** 用户不需要知道 Dify 怎么实现的，需要知道"我怎么实现我的需求"。

## 四、如果要重新设计教程

### 结构应该是这样

```
第一课：你的第一个工作流（15 分钟）
  → 只讲 Start → LLM → End
  → 拖拽 + 填文字 + 点运行
  → 目标：让用户在 10 分钟内看到"能跑"

第二课：让 AI 更聪明（30 分钟）
  → System Prompt 怎么写
  → 变量怎么传递（模板里的 {{}} 怎么用）
  → 加一个 Code 节点处理 LLM 输出

第三课：连上外部世界（30 分钟）
  → HTTP 节点调 API
  → 知识库检索让 LLM 读文档
  → 环境变量管理密钥

第四课：分支和循环（45 分钟）
  → IF-ELSE 做智能路由
  → 迭代批量处理
  → 问题分类器 + 参数提取

第五课：做一个完整项目（60 分钟）
  → 选一个场景，从头搭到尾
  → 包含：错误处理、调试技巧、发布上线
```

每课的核心公式：**"你要做什么 → 为什么这样做 → 跟着我一步一步做 → 你应该看到什么 → 常见错误怎么修"**

### 实操内容必须包含

每个动手步骤至少包含：
1. **具体操作**（点哪里、填什么、选什么）
2. **预期结果**（出现什么画面、返回什么数据）
3. **验证方法**（怎么确认做对了）
4. **排错指南**（如果不对，检查哪 3 项）

## 五、沉淀为记忆

这次的核心教训：

1. **DSL 文件生成**：必须逐字段对照官方测试用例，不能凭经验写
2. **workflow ≠ chatflow**：两种模式下的可用变量不同，`memory.query_prompt_template` 引用必须匹配模式
3. **教程的目标用户决定内容深度**：给小白看的教程要从"点哪里"开始，源码路径是噪音
4. **实操 = 操作步骤 + 预期结果 + 验证方法 + 排错指南**，缺一不可
