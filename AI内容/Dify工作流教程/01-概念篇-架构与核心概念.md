# 第一篇：概念篇 — 工作流架构与核心概念

> 读完本篇你会理解：Dify 工作流到底是什么、怎么运转的、有哪些组成部分。这是搭建任何工作流前必须掌握的基础。

---

## 1. 什么是 Dify 工作流？

Dify 工作流是一个**可视化编排 LLM 应用的画布**。你可以把它理解为：

```
输入 → [节点A] → [节点B] → [节点C] → 输出
               ↓
         [节点D (条件分支)]
               ↓
         [节点E]
```

每个方框是一个**节点**（Node），箭头是**边**（Edge），整体构成一张**有向图**（Directed Graph）。

底层引擎叫 **Graphon**（源码 `graphon/`），Dify 在此之上加了 LLM 配额、可观测性等业务层（源码 `api/core/workflow/workflow_entry.py`）。

### 1.1 工作流入口（WorkflowEntry）

```python
# api/core/workflow/workflow_entry.py
def iter_dify_graph_engine_events():
    """将 GraphEngine 事件转为 Dify 兼容的响应流"""
```

每次运行工作流时：
1. 解析图配置（graph_config）→ 获取 nodes + edges
2. 初始化变量池（VariablePool）→ 注入系统变量
3. 创建 GraphEngine → 从起始节点开始执行
4. 节点按拓扑顺序依次执行 → 输出流式事件

## 2. 三层架构

Dify 工作流的代码架构分三层：

```
┌──────────────────────────────────────┐
│  前端面板层 (web/app/components/)     │  ← React Flow 画布 + 节点配置面板
│  用户拖拽节点，填写参数               │
├──────────────────────────────────────┤
│  工作流编排层 (api/core/workflow/)    │  ← 节点注册、变量池、模板渲染
│  解析图结构，注入系统变量             │
├──────────────────────────────────────┤
│  图执行引擎 (graphon/)                │  ← 拓扑排序、事件流、变量分段
│  真正"跑"工作流的引擎                 │
└──────────────────────────────────────┘
```

### 2.1 前端画布 (React Flow)

Dify 使用 React Flow 库实现画布。所有节点类型定义在：

```typescript
// web/app/components/workflow/types.ts
export enum BlockEnum {
  Start = 'start',
  End = 'end',
  LLM = 'llm',
  Code = 'code',
  // ... 共 25 种节点类型
}
```

每个节点有一个 `default.ts` 文件定义其默认配置（初始值、输入字段、输出结构）。

### 2.2 节点注册机制

后端节点通过 Python 的 `importlib` + `pkgutil` 自动发现注册：

```python
# api/core/workflow/node_factory.py
def register_nodes() -> None:
    _import_node_package("graphon.nodes")        # 内置节点
    _import_node_package("core.workflow.nodes")  # Dify 自定义节点

def resolve_workflow_node_class(*, node_type, node_version):
    """根据节点类型 + 版本号解析对应的 Node 类"""
```

### 2.3 图执行引擎 (Graphon)

Graphon 负责：
- **拓扑排序**：按依赖顺序决定节点执行先后
- **事件流**：每个节点完成后发出事件（`GraphNodeEventBase`）
- **变量池**：所有变量存储在 `VariablePool`，通过 `(node_id, field_name)` 选择器访问
- **暂停/恢复**：支持人工输入节点暂停工作流

## 3. 28 种节点总览

Dify（当前版本）共有 **28 种节点类型**，分为 5 大类：

### 3.1 流程控制类（6 种）

| 节点 | BlockEnum | 作用 |
|------|-----------|------|
| **开始** | `start` | 工作流入口，定义输入变量 |
| **结束** | `end` | 工作流出口，定义输出变量 |
| **答案** | `answer` | 在 Chat 模式中输出回复 |
| **IF-ELSE** | `if-else` | 条件分支，支持多条件组合 |
| **迭代** | `iteration` | 遍历数组，并行处理 |
| **循环** | `loop` | 条件循环，支持 break 条件 |

### 3.2 AI/LLM 类（5 种）

| 节点 | BlockEnum | 作用 |
|------|-----------|------|
| **LLM** | `llm` | 调用大语言模型 |
| **知识检索** | `knowledge-retrieval` | 从知识库检索相关文档 |
| **问题分类器** | `question-classifier` | 将用户输入分类到预设类别 |
| **参数提取器** | `parameter-extractor` | 从文本中提取结构化参数 |
| **Agent** | `agent-v2` | 自主推理 + 工具调用 |

### 3.3 数据处理类（7 种）

| 节点 | BlockEnum | 作用 |
|------|-----------|------|
| **Code** | `code` | 执行 Python/JS 代码 |
| **模板转换** | `template-transform` | Jinja2 模板渲染文本 |
| **变量赋值器** | `variable-assigner` | 写入/覆盖变量 |
| **变量聚合器** | `variable-aggregator` | 收集多个上游输出 |
| **HTTP 请求** | `http-request` | 调用外部 API |
| **文档提取器** | `document-extractor` | 解析 PDF/Word/Excel |
| **列表操作** | `list-operator` | 过滤/排序数组 |

### 3.4 触发器类（4 种）

| 节点 | BlockEnum | 作用 |
|------|-----------|------|
| **Webhook 触发器** | `trigger-webhook` | HTTP Webhook 触发 |
| **定时触发器** | `trigger-schedule` | 按 Cron 表达式定时触发 |
| **插件触发器** | `trigger-plugin` | 第三方插件触发 |
| **数据源** | `datasource` | 从外部数据源拉数据触发 |

### 3.5 交互/特殊类（6 种）

| 节点 | BlockEnum | 作用 |
|------|-----------|------|
| **工具** | `tool` | 调用内置/自定义插件工具 |
| **人工输入** | `human-input` | 暂停等待人工操作 |
| **知识库索引** | `knowledge-index` | 创建/更新知识库 |

（部分旧版本/占位节点不一一列举）

## 4. 工作流执行模型

### 4.1 拓扑排序 — 谁先执行？

工作流引擎从**起始节点**（Start/DataSource/Trigger）出发，按边的方向依次执行后续节点。

```
[Start] → [HTTP 请求] → [LLM] → [End]
            ↓
         [Code]
```

上图中，HTTP 请求和 Code 作为 LLM 的上游节点，会**先于** LLM 执行。引擎通过 `WorkflowGraphTopology` 类判断节点间的上下游关系：

```python
# api/core/workflow/graph_topology.py
class WorkflowGraphTopology:
    def is_upstream(self, *, source_node_id, target_node_id):
        """BFS 判断 source 是否在 target 的上游"""
```

### 4.2 流式事件 — 怎么知道运行到哪了？

每次执行产生流式事件（SSE），前端通过事件驱动更新 UI：

```python
# 事件类型
- GraphNodeEventBase       ← 节点开始/完成
- GraphEngineEvent         ← 引擎层事件
- GraphRunFailedEvent      ← 执行失败
```

前端通过事件更新节点运行状态（`NodeRunningStatus`），实现实时高亮。

### 4.3 并行执行

迭代（Iteration）节点内部支持**并行执行**：

```typescript
// web/app/components/workflow/constants.ts
export const MIN_ITERATION_PARALLEL_NUM = 1
```

当迭代数组有 10 个元素且并行度设为 5 时，引擎同时处理 5 个元素。

## 5. 变量系统初步

变量是工作流的血液。每个节点的输出都存在变量池里，下游节点通过**选择器**（Selector）引用。

### 5.1 变量池（VariablePool）

```python
# api/core/workflow/variable_pool_initializer.py
def add_variables_to_pool(variable_pool, variables):
    for variable in variables:
        variable_pool.add(variable.selector, variable)

def add_node_inputs_to_pool(variable_pool, *, node_id, inputs, aliases=()):
    """将节点输入存入变量池，key 为 (node_id, key) 元组"""
```

变量池本质上是一个以 `(node_id, field_name)` 为 key 的 KV 存储。

### 5.2 系统变量

每个工作流自动注入以下系统变量（源码 `system_variables.py`）：

```python
class SystemVariableKey(StrEnum):
    QUERY = "query"                    # 用户输入
    FILES = "files"                    # 上传文件
    CONVERSATION_ID = "conversation_id"
    USER_ID = "user_id"
    DIALOGUE_COUNT = "dialogue_count"  # 对话轮次
    APP_ID = "app_id"
    WORKFLOW_ID = "workflow_id"
    WORKFLOW_EXECUTION_ID = "workflow_run_id"
    TIMESTAMP = "timestamp"
```

前端引用为：`sys.query`、`sys.user_id`、`sys.files` 等。

### 5.3 变量引用方式

在节点配置中可以通过 `{{变量}}` 或变量选择器引用：

- **系统变量**：`sys.query`、`sys.user_id`
- **上游节点输出**：`{{节点ID.输出字段}}`，如 `{{17200001.text}}`
- **环境变量**：`env.API_KEY`
- **对话变量**：`conversation.xxx`（仅 Chat 模式）

详细机制见 [变量篇](03-变量篇-变量系统与数据传递.md)。

## 6. 两种运行模式

### 6.1 Workflow 模式（工作流应用）

```
用户输入 → [Start] → [处理链] → [End] → 最终输出
```

- 类型：`AppMode.WORKFLOW`
- 无对话上下文（每次独立运行）
- 输出由 End 节点的 `outputs` 定义

### 6.2 Chat 模式（聊天应用）

```
用户消息 → [Start] → [处理链] → [Answer] → 回复
```

- 类型：`AppMode.CHAT`
- 有对话上下文（`sys.conversation_id`、`sys.dialogue_count`）
- 输出由 Answer 节点给出

### 6.3 Agent 模式

用 Agent 节点构建的自主代理类型，Agent 内部可调用工具和子工作流。

---

## 7. 开始搭建前必知的 8 件事

1. **Start 节点决定输入** — 工作流能接收什么参数，取决于 Start 的输入变量定义。
2. **End 节点决定输出** — 最终返回什么数据，取决于 End 的输出变量配置。
3. **变量引用必须依赖边** — 只有通过边连上的上游节点输出才能被引用。
4. **迭代/循环创建子作用域** — 内部的变量在外部不可见（见变量篇）。
5. **分支默认并行** — IF-ELSE 的各分支会按条件选择执行，不是全部执行。
6. **LLM 节点必须配模型** — 需要在 Dify 设置中先配置模型供应商。
7. **Code 节点有执行限制** — 沙箱环境，不能访问外部网络/文件系统（除非配置开启）。
8. **发布后才能被 API 调用** — 画布上的工作流需要"发布"（Publish）才能通过 API 或触发器访问。
