## 案例 1：智能客服机器人（入门级）

### 场景
搭建一个能回答产品问题、查询订单的智能客服。

### 工作流结构

```
                    ┌→ [LLM: 知识库客服] → [Answer]
[Start] → [问题分类器] →
                    └→ [知识检索] → [模板转换] → [LLM: 产品顾问] → [Answer]
```

### 第 1 步：创建 Start 节点

添加一个输入变量 `query`（文本类型，默认值为空）。

### 第 2 步：问题分类器

添加 3 个分类：

| 类名 | 标签 | 描述 |
|------|------|------|
| 订单查询 | `order` | 用户询问订单状态、物流、退款 |
| 产品咨询 | `product` | 用户询问产品功能、价格、使用方法 |
| 其他问题 | `general` | 闲聊、问候、无法归类的其他问题 |

### 第 3 步：配置知识库检索（产品咨询分支）

- 选择包含产品文档的知识库
- 检索模式：混合检索
- TopK：3
- 分数阈值：0.5

### 第 4 步：模板转换 — 拼接检索结果

```jinja2
你是一个专业的产品顾问。请根据以下产品信息回答用户问题：

{% for doc in knowledge_retrieval.result %}
---
参考来源：{{ doc.title }}
{{ doc.content }}
{% endfor %}

用户问题：{{ sys.query }}

要求：
1. 如果信息不足，诚实告知
2. 回答简洁，不超过 200 字
```

### 第 5 步：配置 3 个 LLM 分支

| 分支 | 模型 | System Prompt | User Prompt |
|------|------|--------------|-------------|
| 订单查询 | GPT-4o | "你是订单客服助手" | `{{sys.query}}` |
| 产品咨询 | GPT-4o | "你是产品顾问" | `{{模板转换节点.output}}` |
| 其他问题 | GPT-4o-mini | "你是友好助手" | `{{sys.query}}` |

### 第 6 步：配置 IF-ELSE 路由

不是独立 IF-ELSE，而是问题分类器输出后直接在边上的条件路由中设置：
- `class_label == "order"` → 订单查询分支
- `class_label == "product"` → 产品咨询分支
- `class_label == "general"` → 其他问题分支

### 第 7 步：Answer 和 End

所有 3 条分支都连到各自的 Answer 节点（输出回复文本），再汇聚到 End。

### 关键技巧
- ✅ 问题分类器做第一层路由，降低 LLM 调用成本（general 场景用便宜模型）
- ✅ 知识库检索 + 模板转换构成 RAG 管线
- ✅ 每条分支独立 Answer，方便调试和统计

## 案例 2：RAG 文档问答（中级）

### 场景
用户上传一个文档（PDF/Word），工作流自动解析文档内容并回答用户问题。

### 工作流结构

```
[Start] → [文档提取器] → [Code: 解析文档内容] → [LLM: 基于文档回答] → [End]
```

### 第 1 步：Start 节点

输入变量：
- `query`：文本（用户问题）
- `document`：文件（支持 document 类型）

### 第 2 步：文档提取器

- 输入文件：`{{sys.files}}`（调用时上传的文件）

### 第 3 步：Code 节点 — 格式化文档内容

```python
def main(args):
    # 文档提取器返回的内容
    docs = args.get('doc_extractor_output', [])
    
    content_parts = []
    for doc in docs:
        if isinstance(doc, dict):
            content_parts.append(doc.get('content', ''))
        else:
            content_parts.append(str(doc))
    
    full_text = '\n\n'.join(content_parts)
    
    # 截断过长文本（保留模型上下文窗口）
    max_chars = 8000
    if len(full_text) > max_chars:
        full_text = full_text[:max_chars] + '\n\n[文档过长，已截断...]'
    
    return {
        'document_content': full_text,
        'word_count': len(full_text.split())
    }
```

### 第 4 步：LLM 节点

System Prompt：
```
你是一个文档分析助手。用户会上传一个文档，你需要基于文档内容回答问题。

规则：
1. 只基于文档内容回答，不要编造信息
2. 如果文档中没有相关信息，明确说"文档中未提及"
3. 回答要具体，引用文档中的原文

文档内容如下：
---
{{code_node.document_content}}
---
```

User Prompt：`{{sys.query}}`

### 第 5 步：End 节点

输出变量：
- `answer`：`{{llm_node.text}}`
- `word_count`：`{{code_node.word_count}}`

### 关键技巧
- ✅ Code 节点做内容截断，防止超上下文
- ✅ 明确告知 LLM 不要编造信息（防止幻觉）
- ✅ 输出同时包含答案和统计信息

## 案例 3：API 数据聚合管线（中级）

### 场景
工作流作为 API 聚合器，同时查两个数据源的天气信息，合并后返回。

### 工作流结构

```
                   ┌→ [HTTP: 当前天气 API] → 
[Start:城市名] →    │                       → [Code: 合并数据] → [LLM: 总结] → [End]
                   └→ [HTTP: 天气预报 API] →
```

### 第 1 步：Start

输入变量：
- `city`：文本（城市名）

### 第 2 步：HTTP 请求 A — 当前天气

- URL：`https://api.openweathermap.org/data/2.5/weather?q={{start.city}}&appid={{env.WEATHER_API_KEY}}&lang=zh_cn`
- 方法：GET
- 输出：`current_weather`

### 第 3 步：HTTP 请求 B — 天气预报

- URL：`https://api.openweathermap.org/data/2.5/forecast?q={{start.city}}&appid={{env.WEATHER_API_KEY}}&lang=zh_cn`
- 方法：GET
- 输出：`forecast`

### 第 4 步：Code 节点 — 合并数据

```python
import json

def main(args):
    current_raw = args.get('current_weather_body', '{}')
    forecast_raw = args.get('forecast_body', '{}')
    
    current = json.loads(current_raw)
    forecast = json.loads(forecast_raw)
    
    # 提取当前天气
    now = {
        'temp': current.get('main', {}).get('temp', 0) - 273.15,  # K → °C
        'humidity': current.get('main', {}).get('humidity', 0),
        'description': current.get('weather', [{}])[0].get('description', '未知'),
        'wind_speed': current.get('wind', {}).get('speed', 0),
    }
    
    # 提取未来几天预报（每 3 小时一条，取每天 12:00 的）
    daily = []
    seen_dates = set()
    for item in forecast.get('list', []):
        date = item.get('dt_txt', '').split(' ')[0]
        if date not in seen_dates and '12:00' in item.get('dt_txt', ''):
            seen_dates.add(date)
            daily.append({
                'date': date,
                'temp': item.get('main', {}).get('temp', 0) - 273.15,
                'description': item.get('weather', [{}])[0].get('description', '未知')
            })
    
    return {
        'current': now,
        'daily': daily[:5]  # 最多 5 天
    }
```

### 第 5 步：LLM 总结

System Prompt：
```
你是天气播报员。请根据数据生成简洁的天气报告。

当前天气：温度 {{code.current.temp}}°C，湿度 {{code.current.humidity}}%，{{code.current.description}}
未来天气：
{% for day in code.daily %}
- {{ day.date }}：{{ day.temp }}°C，{{ day.description }}
{% endfor %}
```

### 关键技巧
- ✅ 两个 HTTP 请求之间没有依赖 → 可以并行执行
- ✅ Code 节点做单位转换（K → °C）和数据结构化
- ✅ 环境变量存 API Key，不硬编码

## 案例 4：AI Agent 自动处理邮件（高级）

### 场景
Agent 接收邮件内容，自动判断意图并调用相应工具处理（日历、CRM、知识库）。

### 工作流结构

```
[Start:接收邮件] → [Agent v2] → [End:处理结果]
                      │
                      ├─ Tool: Google Calendar（查询日程）
                      ├─ Tool: CRM（查询客户信息）
                      └─ Tool: 知识库检索（查FAQ）
```

### 第 1 步：Start

输入变量：
- `email_content`：文本（邮件正文）
- `sender_email`：文本（发件人地址）

### 第 2 步：配置 Agent v2 节点

**Agent 策略**：选择 Function Calling（工具调用）。

**模型**：GPT-4o 或 Claude Sonnet 4。

**系统指令**：
```
你是邮件处理助手。根据邮件内容判断意图并调用相应工具：

1. 如果涉及会议/日程安排 → 使用 Google Calendar 工具
2. 如果询问客户信息 → 使用 CRM 查询工具
3. 如果询问产品/服务问题 → 使用知识库检索工具

处理完成后，生成一段简洁的回复草稿。

邮件发件人：{{start.sender_email}}
```

**工具列表**：
1. Google Calendar — 查询/创建日程
2. CRM 客户查询 — 按邮箱查客户信息
3. 知识库搜索 — RAG 检索产品文档

**查询**：`{{start.email_content}}`

### 第 3 步：错误处理配置

在 Agent 节点上：
- 失败时：继续执行
- 设置 fallback 输出：
  ```
  "无法自动处理此邮件，请人工处理。类别：{{问题分类器.class_name}}"
  ```

### 第 4 步：End 节点

输出变量：
- `reply_draft`：`{{agent.text}}`（Agent 生成的回复草稿）
- `actions_taken`：`{{agent.json}}`（执行了哪些工具调用）

### 关键技巧
- ✅ Agent v2 支持结构化 JSON 输出（`agent.json`），方便下游处理
- ✅ 错误处理确保即使 Agent 失败也有兜底回复
- ✅ 多工具场景下，Agent 自动决定调用顺序

## 案例 5：定时数据分析报表（触发器 + 管线）

### 场景
每天上午 9 点自动拉取昨天的销售数据，分析后发送到企业微信。

### 工作流结构

```
[定时触发器(每天9:00)] → [HTTP: 拉取昨日销售数据]
             → [Code: 数据清洗 + 计算指标]
             → [LLM: 生成分析报告]
             → [HTTP: 发送企业微信消息]
             → [End]
```

### 第 1 步：定时触发器

- 类型：定时触发
- Cron 表达式：`0 9 * * *`（每天上午 9:00）
- 无需输入变量

### 第 2 步：HTTP 请求 — 拉取数据

- URL：`https://your-api.com/sales?date={{昨天日期}}&token={{env.API_TOKEN}}`
- 方法：GET

### 第 3 步：Code 节点 — 数据清洗

```python
import json
from datetime import datetime, timedelta

def main(args):
    raw = json.loads(args.get('sales_data_body', '{}'))
    records = raw.get('data', [])
    
    # 基础统计
    total_revenue = sum(r.get('amount', 0) for r in records)
    total_orders = len(records)
    
    # 按产品分类
    by_product = {}
    for r in records:
        product = r.get('product_name', '其他')
        if product not in by_product:
            by_product[product] = {'count': 0, 'revenue': 0}
        by_product[product]['count'] += 1
        by_product[product]['revenue'] += r.get('amount', 0)
    
    # Top 5
    top_products = sorted(
        by_product.items(),
        key=lambda x: x[1]['revenue'],
        reverse=True
    )[:5]
    
    # 与前一天对比
    yesterday = (datetime.now() - timedelta(days=1)).strftime('%Y-%m-%d')
    
    return {
        'total_revenue': total_revenue,
        'total_orders': total_orders,
        'top_products': top_products,
        'report_date': yesterday
    }
```

### 第 4 步：LLM 生成报告

System Prompt：
```
你是销售数据分析师。请根据数据生成简洁的日报。

格式要求：
1. 📊 总览（总营收 + 总订单数）
2. 🏆 Top 5 产品（名称 + 收入 + 占比）
3. 📈 关键发现（不超过 3 条）
4. ⚠️ 需要关注的问题（如有）
```

### 第 5 步：HTTP 请求 — 发送企业微信

- URL：`https://qyapi.weixin.qq.com/cgi-bin/webhook/send?key={{env.WECHAT_WEBHOOK_KEY}}`
- 方法：POST
- Body：
```json
{
  "msgtype": "markdown",
  "markdown": {
    "content": "{{llm_node.text}}"
  }
}
```

### 关键技巧
- ✅ Cron 表达式配置定时
- ✅ 环境变量管理 API Key 和 Webhook URL
- ✅ Code 节点做业务逻辑（比 LLM 更可靠更便宜）
- ✅ 最后一步 HTTP 推送结果，形成闭环

## 通用最佳实践总结

### 命名规范
- ✅ 节点名称清晰描述功能：`LLM-分析邮件` > `LLM1`
- ✅ 中文或英文统一（不要混用）
- ✅ 关键节点加 Note 注释说明业务逻辑

### 错误处理
- ✅ 外部调用（HTTP/Tool）总是启用在错误时继续
- ✅ 关键路径加 IF-ELSE 兜底
- ✅ 设置合理的超时时间

### 性能
- ✅ 昂贵的 LLM（GPT-4o）只用在对质量要求高的节点
- ✅ 简单分类/提取用便宜模型（GPT-4o-mini / Haiku）
- ✅ 能用 Code 节点的逻辑不给 LLM 做

### 调试
- ✅ 先运行单个节点，确认输出结构 → 再连完整工作流
- ✅ 查看运行日志确认每个节点的输入输出
- ✅ 复杂场景先用 mock 数据测试
