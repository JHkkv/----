## 1. LLM — 大语言模型

### 作用
调用大语言模型进行文本生成、推理、分析。

### 核心配置

**模型选择**：在 Dify 设置 → 模型供应商中预先配置。

**提示词**：支持变量插值，引用 `{{上游节点.字段}}`。

```
你是一个专业的数据分析师。请分析以下数据：

{{start.query}}

请从以下维度进行分析：
1. 数据趋势
2. 异常点
3. 改进建议
```

**上下文窗口**：通过"上下文"配置向提示词注入外部文本（如知识库检索结果）。

**记忆（Memory）**：Chat 模式下可开启对话记忆，自动携带历史消息。

### 与源码对应

- 后端：`graphon/nodes/llm/entities.py` → `LLMNodeData`
- 前端面板：`web/app/components/workflow/nodes/llm/`
- 输出结构：

```typescript
// web/app/components/workflow/constants.ts
export const LLM_OUTPUT_STRUCT: Var[] = [
  { variable: 'text', type: VarType.string },
  { variable: 'reasoning_content', type: VarType.string },  // o1/Claude 思考过程
  { variable: 'usage', type: VarType.object },              // Token 用量
]
```

### 常用技巧

1. **System Prompt + User Prompt 分离**：系统提示词设置角色，用户提示词传入实际输入。
2. **用 Jinja2 模板控制输出格式**：要求 LLM 输出 JSON → 下游 Code 节点解析。
3. **使用 reasoning_content**：对推理模型（o1/Claude 等），可通过 `reasoning_content` 获取思考链路。
4. **Vision 多模态**：LLM 节点支持传入图片文件（需选择支持视觉的模型）。

### 避坑

- ❌ 变量引用写错格式（必须 `{{nodeId.fieldName}}`，不是 `{{nodeId.output}}`）
- ❌ 上下文窗口溢出（知识检索结果太长，超出模型限制）
- ❌ 忘记配置错误处理（LLM 调用失败默认终止工作流，建议启用"失败时继续"）

## 2. KnowledgeRetrieval — 知识库检索

### 作用
从 Dify 知识库中检索与查询最相关的文档片段。

### 核心配置

**知识库选择**：选择一个或多个已导入数据的知识库。

**检索模式**：
- **混合检索**（推荐）：关键词 + 语义向量双路召回后融合排序，兼顾精确匹配和语义匹配
- **语义检索**：纯向量相似度，适合长文本、模糊问题
- **全文检索**：纯关键词匹配，适合精确查询（编号、姓名、术语）

**TopK**：返回最相关的 K 个文档片段（默认 3-5）。

**分数阈值**：低于此分数的结果丢弃。

**Rerank（重排序）**：可选启用 Rerank 模型对 TopK 结果再做一次精排。

### 输出结构

```typescript
{ result: [{
  content: string,     // 片段正文
  title: string,       // 所属文档标题
  url: string,         // 文档 URL
  icon: string,
  metadata: {
    dataset_id: string,
    dataset_name: string,
    document_name: string,
    document_data_source_type: string,
    segment_position: number,
    segment_word_count: number,
    segment_hit_count: number,
    score: number
  }
}]}
```

### 常见模式

```
[Start] → [知识检索] → [LLM（拼接检索结果）] → [Answer]
```

在 LLM 的上下文配置中引入 `{{知识检索节点.result}}`。

### 避坑

- ❌ 不设置分数阈值 → 低质量结果污染 LLM 上下文
- ❌ TopK 太大 → 超出模型上下文窗口
- ❌ 只用语义检索查精确值（编号/代码/日期）→ 错配，该用全文检索

## 3. IF-ELSE — 条件分支

### 作用
根据条件判断走不同分支。支持多条件 AND/OR 组合。

### 核心配置

```yaml
条件列表（按顺序匹配）:
  - IF: 条件1 → 分支1
  - ELIF: 条件2 → 分支2
  - ELSE → 分支3（兜底）
```

**支持的条件类型**：
- `is` / `is not` — 等于/不等于
- `contains` / `not contains` — 包含/不包含
- `starts with` / `ends with`
- `is empty` / `is not empty`
- `greater than` / `less than` — 数值比较
- `in` / `not in` — 集合包含

**条件组合**：多个条件可通过 AND（全部满足）或 OR（任一满足）组合。

**条件来源**：支持引用变量、常量、系统变量。

### 前端实现

```typescript
// web/app/components/workflow/nodes/if-else/components/condition-list/condition-input.tsx
```

### 常见模式

```yaml
# 意图路由
IF sys.query 包含 "退款" → 退款处理分支
ELIF sys.query 包含 "退货" → 退货处理分支
ELSE → 智能客服分支
```

### 避坑

- ❌ 分支逻辑不互斥导致第一个 IF 始终命中
- ❌ 忘记 ELSE 兜底（没有匹配条件会报错）
- ❌ 深层嵌套 IF-ELSE（超过 3 层考虑用问题分类器）

## 4. Code — 代码执行

### 作用
在沙箱中执行 Python 或 JavaScript 代码，处理复杂数据转换。

### 核心配置

**语言**：Python3 或 JavaScript（Node.js）。

**输入变量**：声明代码中引用的上游变量，名称需与 `args.变量名` 一致。

**代码**：在 `main` 函数中编写逻辑，返回 dict/object。

```python
def main(args):
    # args 是输入变量
    text = args.get('input_text', '')
    
    # 处理逻辑
    word_count = len(text.split())
    lines = text.split('\n')
    
    # 返回 dict — 成为下游可引用的输出
    return {
        'word_count': word_count,
        'line_count': len(lines),
        'summary': text[:200] + '...' if len(text) > 200 else text
    }
```

### 沙箱限制

- 默认无外部网络访问
- 无文件系统写权限（可读临时文件）
- 执行超时限制
- 内存限制

```python
# api/core/workflow/nodes/code/entities.py
class CodeLanguage:
    PYTHON3 = "python3"
    JAVASCRIPT = "javascript"
```

### 常见模式

```python
# 1. JSON 解析与聚合
def main(args):
    import json
    results = args['items']  # 迭代/聚合的输出数组
    merged = []
    for item in results:
        merged.append({
            'name': item['name'],
            'score': float(item['score'])
        })
    return {
        'merged': merged,
        'avg_score': sum(x['score'] for x in merged) / len(merged)
    }

# 2. 数据清洗
def main(args):
    text = args['raw_text']
    # 去除首尾空白、统一换行符
    cleaned = text.strip().replace('\r\n', '\n')
    return {'cleaned': cleaned}
```

### 避坑

- ❌ 在 Code 节点中执行耗时操作（超时限制严格，大数据处理拆成多个节点）
- ❌ 返回值不是可序列化对象（不能返回 class 实例，只能是 dict/list/str/int/float/bool/None）
- ❌ 忘记在"输入变量"中声明引用 → 代码中 `args['xxx']` 为空

## 5. HTTPRequest — HTTP 请求

### 作用
在工作流中调用任何外部 REST API。

### 核心配置

| 参数 | 说明 |
|------|------|
| 请求方法 | GET / POST / PUT / PATCH / DELETE / HEAD |
| URL | 支持变量插值 `https://api.example.com/users/{{id}}` |
| 请求头 | Key-Value，支持引用变量 |
| 请求体 | JSON / Form-Data / x-www-form-urlencoded / Raw Text / Binary |
| 授权 | None / Bearer Token / Basic Auth / API Key（Header/Cookie/Query）|
| 超时 | 默认 10s，可调 |

### 输出结构

```typescript
// web/app/components/workflow/constants.ts
{
  body: string,          // 响应体（文本）
  status_code: number,   // HTTP 状态码
  headers: object,       // 响应头（Key-Value）
  files: File[]          // 响应文件
}
```

### 常见模式

```yaml
# 模式 1：Agent 调用外部数据源
[Start] → [HTTP: 调企业CRM API查客户] → [Code: 格式化数据] → [LLM: 生成客户报告] → [End]

# 模式 2：工作流作为 API 聚合器
[Webhook] → [HTTP: API-A] → [HTTP: API-B] → [Code: 合并结果] → [End]
# 注：如果两个 API 互相独立，可用 IF-ELSE + 并行分支同时调用
```

### 避坑

- ❌ 响应体不是 UTF-8 编码（乱码）
- ❌ 不处理 HTTP 错误状态码（4xx/5xx 导致节点失败，建议开启"失败时继续"）
- ❌ URL 参数未编码（中文/特殊字符需 URL encode）

## 6. TemplateTransform — 模板转换

### 作用
使用 Jinja2 模板引擎将变量渲染为文本。

### 核心配置

**模板内容**：Jinja2 语法，支持变量、过滤器、控制流。

```jinja2
# 示例：将检索结果格式化为 LLM 可读的上下文
以下是与"{{ sys.query }}"相关的知识库内容：

{% for item in knowledge_retrieval.result %}
---
文档：{{ item.title }}
来源：{{ item.url }}

{{ item.content }}
{% endfor %}

请基于以上信息回答用户问题。
```

### 常用 Jinja2 语法

```jinja2
{# 变量 #}
{{ variable_name }}

{# 过滤器 #}
{{ text | upper }}
{{ text | truncate(100) }}
{{ items | length }}
{{ date | default('未知') }}

{# 循环 #}
{% for item in items %}
- {{ loop.index }}. {{ item.name }}
{% endfor %}

{# 条件 #}
{% if score > 0.8 %}
匹配度高
{% elif score > 0.5 %}
匹配度中
{% else %}
匹配度低
{% endif %}
```

### 避坑

- ❌ 模板语法错误（Jinja2 报错不直观，先用简单模板测试）
- ❌ 变量不存在导致渲染为空白（用 `| default()` 防御）
- ❌ 用模板做复杂数据处理（逻辑量 > 10 行 → 用 Code 节点）

## 7. Start — 开始节点

### 作用
定义工作流的输入变量。每个工作流必须有且仅有一个 Start 节点。

### 输入变量类型

| 类型 | 说明 |
|------|------|
| 文本 | 单行/多行文本 |
| 段落 | 长文本 |
| 数字 | 数值 |
| 文件 | 文件上传（支持 image/document/audio/video） |
| 下拉选项 | 预设选项 |

### 系统变量（自动注入）

```
sys.query      — 用户输入文本
sys.files      — 上传的文件列表
sys.user_id    — 用户 ID（WebApp/API 调用方）
sys.app_id     — 应用 ID
sys.workflow_id       — 工作流 ID
sys.workflow_run_id   — 本次运行 ID
sys.dialogue_count    — 对话轮次（仅 Chat 模式）
sys.conversation_id   — 对话 ID（仅 Chat 模式）
sys.timestamp         — 触发时间戳（仅 Workflow 模式）
```

## 8. End — 结束节点

### 作用
定义工作流的输出。所有路径最终都应该汇聚到 End 节点。

### 配置

- **输出变量**：选择要暴露给调用方的变量。
- 可以输出多个变量，变量名即为 API 响应 JSON 的 key。

```json
// API 调用返回示例
{
  "result": "分析完成",
  "score": 85,
  "suggestions": ["建议1", "建议2"]
}
```

### 避坑

- ❌ IF-ELSE 的某些分支没有连到 End → 工作流在那条路径永远不返回结果
- ❌ 输出变量引用了范围外的变量（迭代/循环内部变量在外部不可见）

---

## 9. Answer — 答案节点

### 作用
仅在 **Chat 模式**中使用，生成用户可见的回复消息。与 End 的区别：Answer 是聊天回复的内容，End 是 API 返回值。

### 与 End 的配合

```
[LLM] → [Answer]   ← 用户看到的回复
      ↘ [End]       ← API 返回的结构化数据
```

## 10. VariableAssigner — 变量赋值器

### 作用
在工作流执行过程中写入/覆盖变量的值。类似于编程中的 `=` 赋值。

### 典型场景
- 处理开始输入后需要将中间计算结果持久化
- 聚合多个分支的结果到一个变量
- 对会话变量的增量写入

### 配置

```yaml
变量名: user_topic
值: {{llm_node.text}}
```

### 避坑

- ❌ 写入的变量名与系统变量冲突
- ❌ 在迭代内部写入的变量外部不可见（子作用域隔离）

## 11. QuestionClassifier — 问题分类器

### 作用
使用 LLM 将用户输入分类到预设类别，并输出类别标签。

### 核心配置

定义一个或多个**分类**，每个分类包含：
- **类别名称**（class_name）
- **标签**（class_label）：作为 IF-ELSE 条件的判断值

```yaml
分类 1:
  name: "退款申请"
  label: "refund"
  描述: "用户要求退款、取消订单、找回支付金额"

分类 2:
  name: "商品咨询"
  label: "product_inquiry"
  描述: "用户询问商品信息、规格、库存、价格"
```

### 输出

```json
{
  "class_name": "退款申请",
  "class_label": "refund",
  "usage": { ... }
}
```

### 配合 IF-ELSE 做意图路由

```
[Start] → [问题分类器] → [IF-ELSE]
                           ├─ class_label == "refund" → [退款处理]
                           ├─ class_label == "product_inquiry" → [咨询处理]
                           └─ ELSE → [通用客服]
```

### 避坑

- ❌ 分类描述不够精确（LLM 容易误分类）
- ❌ 类别过多（>10 个时分类准确率下降，考虑拆成两层分类器）
- ❌ 不用 IF-ELSE 处理未知类别（ELSE 兜底很重要）

## 12. ParameterExtractor — 参数提取器

### 作用
使用 LLM 从非结构化文本中提取结构化参数。适合自然语言输入 → 结构化数据。

### 核心配置

定义要提取的参数，每个参数包含：
- **名称**
- **类型**（文本/数字/布尔/选择/数组）
- **描述**（告诉 LLM 如何提取）
- **是否必填**

```yaml
参数:
  - name: city
    type: text
    description: "用户提到的城市名"
    required: true
  - name: budget
    type: number
    description: "预算金额，单位元"
    required: false
  - name: travel_dates
    type: array[text]
    description: "旅行日期列表"
    required: false
```

### 与"从工具导入"配合

可以从已安装的插件工具中一键导入参数定义，保持工具调用和参数提取的一致性。

## 14. DataSource — 数据源

### 作用
将外部数据源的内容作为工作流的起始输入。与 Start 的区别：DataSource 自动从数据库/API 等拉取数据作为输入。

### 与触发器的区别

| 类型 | 作用 |
|------|------|
| Start | 被动接收输入（API 调用时传入） |
| DataSource | 主动拉取数据（从外部源拉） |
| Trigger | 自动触发工作流执行（定时/Webhook/事件） |

---

## 15. ListFilter — 列表过滤器

### 作用
对数组类型的变量进行过滤、排序、去重等操作。

### 配置

```yaml
变量: {{迭代节点.output}}
过滤条件:
  - 字段: score
    条件: greater_than
    值: 0.8
排序: score DESC
限制: 10
```

### 避坑

- ❌ 过滤的字段名与数据中实际字段名不一致（区分大小写）
- ❌ 对空数组操作不设默认值

## 16. 其他节点简表

| 节点 | 用途 | 关键点 |
|------|------|--------|
| **Tool** | 调用已安装的插件工具 | 需要先在"工具"页面安装插件 |
| **迭代 (Iteration)** | 并行处理数组 | 内部是一个子工作流；见进阶篇 |
| **循环 (Loop)** | 条件循环 | 包含 LoopStart + LoopEnd；见进阶篇 |
| **变量聚合器** | 收集多条上游输出为数组 | 适合配合迭代使用 |
| **知识库索引** | 创建/更新知识库 | 用于数据预处理管线 |
| **赋值器 (Assigner)** | 旧版变量赋值，与 VariableAssigner 功能同 | 新项目直接用 VariableAssigner |
| **HumanInput** | 暂停工作流等待人工操作 | 见进阶篇 HITL |
| **触发器 (3类)** | 自动触发工作流 | Webhook/定时/插件；见进阶篇 |
| **Note** | 画布上的注释 | 不参与执行，纯视觉辅助 |
