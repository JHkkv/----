HITL — 01

HITL — 05

HITL 暂停 / 恢复机制

暂停流程

# HumanInput 节点执行时 def pause_workflow(state): # 1. 保存当前 GraphRuntimeState runtime_state = save_state( variables, # 变量池 execution_position, # 执行位置 node_states # 各节点状态 ) # 2. 创建 PauseState 持久化记录 pause = create_pause_record( state=runtime_state, form_schema=human_input_form ) # 3. 发出暂停事件 → 引擎停止 emit_pause_event(pause)

恢复流程

# 人工操作完成后 def resume_workflow(pause_id, form_data): # 1. 加载 PauseState pause = load_pause_record(pause_id) # 2. 将填写的表单数据注入变量池 inject_variables( pause.runtime_state, form_data # 人工填写的数据 ) # 3. 从暂停点恢复引擎执行 engine.resume_from(pause.execution_position)

核心文件：api/core/workflow/nodes/human_input/boundary.py

HITL — 06

HITL 避坑 3 条

❌

超时设置太短

人工操作可能需要几小时甚至几天（如跨时区审批）。设置过短的超时会导致任务过早失败。建议至少 24 小时，重要审批可设 7 天。

❌

没有设计超时后的默认行为

超时后自动通过？自动拒绝？还是回退到上级审批？必须提前配置超时策略，否则工作流会一直卡在等待状态，无法正常终结。

❌

表单字段太多

控制在 5 个以内。字段越多，人工填写意愿越低，处理时间越长。只收集决策必需的信息，其他可通过上游 LLM 自动提取。

ITERATION vs LOOP

迭代 vs 循环 — 如何选择

特性迭代 (Iteration)循环 (Loop)
输入数组任意条件
并行执行支持不支持（串行）
退出方式数组遍历完自动退出条件满足时退出
适用模式"对每个 X 做 Y""重复做直到 Z"
顺序保证不保证（并行模式下）严格按序执行
适用场景批量翻译/总结/审核递归搜索/迭代优化/多轮对话

选择规则

你知道有多少次（有数组）→ 迭代    你不知道多少次（有条件）→ 循环

ITERATION/LOOP — PITFALLS

迭代 / 循环 — 避坑 4 条

变量作用域隔离

迭代/循环内部定义的变量，外部看不到。如果需要把内部结果传递出去，必须通过迭代/循环的输出变量（output）来传递。

循环必须设置最大次数

没有最大次数限制的循环是死循环炸弹。建议根据业务场景设置合理上限，如 10 / 50 / 100，超出后走错误处理分支。

迭代并行度过大导致限流

并行度设太高会超出 LLM API 的并发限制（通常是 RPM/TPM）。建议先确认 API 的并发上限，然后设置并行度为上限的 50%-70%。

迭代内昂贵 LLM 调用 x N = 成本爆炸

如果数组有 100 个元素，每个都调用一次 GPT-4o，成本会非常高。考虑先用便宜模型筛选，或合并请求减少调用次数。

ERROR HANDLING — 01

三种错误处理模式

Dify 提供 3 种错误处理策略，定义在 ErrorHandleMode：

// web/app/components/workflow/types.ts enum ErrorHandleMode { Terminated = 'terminated', // 终止工作流（默认） ContinueOnError = 'continue-on-error', // 失败时继续 RemoveAbnormalOutput = 'remove-abnormal-output' // 移除异常输出后继续 }

Terminated（终止）

默认策略；节点失败立即终止。适合关键节点：数据验证、安全检查。

ContinueOnError（跳过）

失败后跳过该节点继续执行。下游引用失败节点输出得到空值。适合外部 API、可选增强。

RemoveAbnormalOutput（移除异常）

移除失败输出继续执行。适合并行分支中单个分支失败不影响整体。

ERROR HANDLING — 02

错误处理最佳实践表

节点类型推荐策略原因
LLM Terminated 核心推理环节，失败意味着输出不可用
HTTP ContinueOnError 外部服务不稳定，失败不应中断主流程
Tool ContinueOnError 第三方工具可能出错，需容错
Code Terminated 代码逻辑错误应暴露而非静默跳过
Agent ContinueOnError Agent 多步执行，单步失败不应终止整个 Agent

这是生产环境推荐配置，具体可根据业务关键性调整。

错误处理完整策略 Checklist

策略选择

HTTP/Tool/Agent 节点 → ContinueOnError

# RRF (Reciprocal Rank Fusion) 核心算法 — Code 节点 def main(args): results_a, results_b, results_c = args.get('retrieval_a_result',[]), args.get('retrieval_b_result',[]), args.get('retrieval_c_result',[]) scores, k = {}, 60 # k=60 是 RRF 经典常数 for results in [results_a, results_b, results_c]: for rank, doc in enumerate(results): doc_id = doc.get('metadata',{}).get('document_id','') scores[doc_id] = scores.get(doc_id, 0) + 1 / (k + rank + 1) all_docs = {doc['metadata']['document_id']:doc for r in [results_a,results_b,results_c] for doc in r} merged = sorted(all_docs.values(), key=lambda d: scores.get(d['metadata']['document_id'],0), reverse=True)[:10] return {'merged_results': merged}
ADVANCED PATTERNS — 02

条件发布管道

AI 生成内容后，按质量分数走不同处理路径。

LLM
生成内容
→
IF
质量检查
→
score > 0.8 → 直接发布
score > 0.5 → LLM 优化 → 发布
score < 0.5 → HumanInput
人工改写 → 发布

score > 0.8

高质量内容，无需人工审核，直接自动发布。适合对时效性要求高的场景。

score 0.5-0.8

中等质量，交给 LLM 优化后自动发布。节省人工但保证一定质量。

score < 0.5

低质量，触发 HumanInput 人工介入。确保关键内容有人类把关。
