案例 1 — 关键技巧总结

❶ 分类器做入口分流

问题分类器比 LLM 做意图识别 更快更稳定（确定性路由 vs 概率输出）。分类后用 IF-ELSE 实现确定性分支，避免 LLM 幻觉导致错误路由。

❷ 检索阈值是安全阀

Score 阈值 0.5 过滤低相关度片段。TopK=3 + 阈值过滤后若为空，LLM 通过 System Prompt 规则诚实告知 "暂无相关信息"，避免编造。

❸ 按分支选模型节省成本

订单/通用分支用 gpt-4o-mini（便宜快速），产品顾问用 gpt-4o（精准可靠）。按场景需求选模型，可将成本降低 60%+。

延伸思考：如果用户连续多轮对话，需要加入 会话变量 存储上下文，并在 System Prompt 中携带历史记录。

案例 2 — Step 3：Code 节点完整实现

Python 代码 — 文档内容格式化 + 截断

def main(doc_text: str, question: str) -> dict: """格式化文档内容并截断到 8000 字，构造 Prompt 上下文""" # 1. 基本清洗：去除多余空白 cleaned = "\n".join( line.strip() for line in doc_text.split("\n") if line.strip() ) # 2. 截断：保留前 8000 个字符 MAX_CHARS = 8000 if len(cleaned) > MAX_CHARS: cleaned = cleaned[:MAX_CHARS] + "\n\n[... 文档过长，已截断 ...]" # 3. 统计信息 total_chars = len(doc_text) used_chars = len(cleaned) return { "formatted_text": cleaned, "total_chars": total_chars, "used_chars": used_chars, "question": question, "truncated": total_chars > MAX_CHARS, }

为什么截断 8000 字？ 大多数 LLM 上下文窗口 ~4K-8K tokens，8000 中文字 ≈ 12000 tokens，留足余量给 System Prompt 和回答空间。

案例 2 — 关键技巧总结

❶ 防幻觉三件套

(1) System Prompt 明确 只能基于文档回答；(2) 设定拒绝话术模板；(3) 告诉用户文档是否被截断（增进透明度）。

❷ Code 做预处理

文档提取器输出的原始文本常有 多余空白和特殊字符。Code 节点清洗并截断，使 LLM 收到的上下文干净整洁，回答质量显著提升。

❸ 大文档分批策略

超过 8000 字的文档：用 Code 节点 按段落分割后分批调用 LLM（需要循环迭代节点），每批独立问答，最后合并结果。

适用场景：合同审查、论文研读、技术文档问答、规章制度查询。任何需要"基于文件内容精准回答"的场景都可以用此模式。

def main(current_json: dict, forecast_json: dict) -> dict: """合并两个天气 API 数据，提取关键信息""" # 1. 当前天气数据提取 current = { "temp": round(current_json["main"]["temp"], 1), "feels_like": round(current_json["main"]["feels_like"], 1), "humidity": current_json["main"]["humidity"], "description": current_json["weather"][0]["description"], "wind_speed": current_json["wind"]["speed"], } # 2. 温度 K → °C 转换（如果 API 未指定 metric） if current["temp"] > 100: current["temp"] = round(current["temp"] - 273.15, 1) current["feels_like"] = round(current["feels_like"] - 273.15, 1) # 3. 预报数据：取每日 12:00 的代表性数据 daily_forecast = [] for item in forecast_json["list"]: if "12:00:00" in item["dt_txt"]: daily_forecast.append({ "date": item["dt_txt"][:10], "temp": round(item["main"]["temp"], 1), "desc": item["weather"][0]["description"], }) # 4. 取未来 5 天 daily_forecast = daily_forecast[:5] return { "current": current, "forecast": daily_forecast, "city": current_json.get("name", "Unknown"), }

案例 3 — 关键技巧总结

❶ 并行 HTTP 提效

两个 HTTP 节点不相互依赖时，Dify 自动 并行执行。总耗时 = max(请求1, 请求2) 而非 sum。多个独立 API 调用要充分利用此特性。

❷ Code 做数据转换

API 返回的原始 JSON 通常冗余且格式不统一。用 Code 节点做 清洗 + 结构化 + 计算（如 K→°C 转换），LLM 收到的数据干净且可直接使用。

❸ env 管理密钥

使用 {{env.WEATHER_API_KEY}} 引用环境变量，不将 API Key 写死在节点配置中。同一工作流可导出到不同环境，只需修改 env 值。

扩展思路：此模式适用于任何"多源数据聚合"场景 — 股票数据(多交易所)、物流追踪(多快递商)、舆情监控(多社交媒体平台)。

案例 4 — Step 3-4：错误处理 + End 输出

Step 3: IF-ELSE 错误处理

Agent 执行可能失败（工具超时/API限流/推理异常），需要 fallback 机制：

IF Agent.status == "succeeded" → 正常输出 Answer ELSE # Agent 执行失败 → LLM Fallback：生成通用回复模板 → 告知用户"系统暂时无法处理，请稍后重试"

案例 4 — 关键技巧总结

❶ Agent vs 固定分支

案例1 用 IF-ELSE + 分类器做 确定性路由（可预测、快速）。案例4 用 Agent 做 自主推理（灵活、适合开放场景）。根据需求选择正确范式。

❷ 最大迭代设上限

Agent 可无限循环调用工具，需设置 最大迭代次数（建议 5-10 轮）防止陷入死循环或消耗过多 Token。超过上限自动终止并输出已有结果。

❸ Fallback 保底输出

Agent 失败时不要静默报错。用 IF-ELSE 检测 Agent.status，失败时走 Fallback 分支生成友好的"稍后重试"消息，保证用户体验不中断。

安全提醒：Agent 自动发邮件前务必加 人工审核节点(HITL)，避免 AI 幻觉导致错误回复发给客户。进阶篇中将详细讲解 HITL 配置。

案例 5 — Step 1-2：Cron 触发器 + HTTP 拉数据

Step 1: Cron 触发器

将 Start 节点替换为 定时触发器(Cron Trigger)：

# Cron 表达式 0 9 * * * # 含义：每天 9:00 执行 # ┌──── 分钟 (0) # │ ┌── 小时 (9) # │ │ ┌ 日期 (* = 每天) # │ │ │ ┌ 月份 (* = 每月) # │ │ │ │ ┌ 星期 (* = 每星期) # 0 9 * * *

其他常用表达式：
0 */6 * * * — 每6小时
0 9 * * 1 — 每周一早9点

Step 2: HTTP 拉取业务数据

添加 HTTP 请求 节点拉取昨天的业务数据：

# 方法：GET URL： https://api.example.com/v1/dashboard ?date={{yesterday}} &metrics=revenue,orders,users Headers： Authorization: Bearer {{env.API_TOKEN}}

注意：Cron 触发的工作流没有用户输入，需在 HTTP 节点中 硬编码查询参数 或使用 Dify 内置变量。

Step 4: LLM 生成 Markdown 报告

System Prompt 中的格式要求：

你是一个数据分析师。 请根据数据生成 Markdown 格式日报。 报告结构： 1. **标题**：{{ date }} 业务日报 2. **核心指标**：营收/订单/客单价 3. **Top 5 产品**：用列表展示 4. **关键洞察**：与昨日对比的亮点/异常 5. **建议**：1-2 条改进建议 要求：简洁专业，800 字以内。

案例 5 — 关键技巧总结

❶ Cron 语法要测试

Cron 配置错误会导致报表不触发。建议先用 每5分钟（*/5 * * * *）测试，确认无误后再改为目标时间。Dify 控制台可见下次执行时间。

❷ 数据异常要告警

在 Code 节点中检测 异常指标（如营收暴跌 50%），通过 IF-ELSE 走单独的告警分支，发送 @所有人 消息或调用电话告警 API。

❸ 幂等性设计

定时任务可能因重试而重复执行。在 Code 节点中检查 数据日期，如果当天的报告已生成过则跳过，避免群内重复推送。

扩展方向：加入多个 Cron 触发器（早报 + 晚报 + 周报），通过 trigger_type 变量区分不同周期，一份工作流覆盖所有定时场景。

通用最佳实践总结

📝 命名规范

  • ✔ 节点名 = 前缀_功能
    如 LLM_订单客服、HTTP_天气API
  • ✔ 变量用 snake_case
    如 api_response、user_id
  • ✔ 输出描述写清楚
    字段名 + 类型 + 示例值

⚠ 错误处理

  • ✔ 每个 HTTP 后加 状态码检查
    IF status != 200 → Fallback
  • ✔ Agent 必须设 max_iterations
  • ✔ Code 节点 try-except 包裹
    任何异常都返回结构化错误

⚡ 性能优化

  • ✔ 独立节点 自动并行
  • ✔ 简单任务用 便宜模型
  • ✔ 知识库检索设 Score 阈值
    减少 LLM 上下文大小

🔍 调试技巧

  • ✔ 用 Preview 模式 单步执行
  • ✔ 中间加 Template 节点 查看变量
  • ✔ 用 日志 Webhook 记录关键路径
    记录到 Lark/飞书/企微做监控
黄金法则：先跑通最简单的线性流程，再逐步添加分支、错误处理、并行优化。不要一开始就追求完美架构。
