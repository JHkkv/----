AI/LLM #1

LLM — 大语言模型节点

调用大语言模型进行文本生成、推理、分析

核心配置

模型选择：在 Dify 设置 → 模型供应商中预配置

提示词：支持 {{变量}} 插值，引用上游节点字段

上下文：注入外部文本（知识库检索结果等）

记忆 (Memory)：Chat 模式下可开启对话记忆

输出结构

字段类型说明
textstringLLM 生成的文本
reasoning_contentstring思考过程 (o1/Claude)
usageobjectToken 用量统计

常用技巧

  • System/User 分离：System Prompt 设角色，User Prompt 传实际输入
  • Jinja2 控制格式：要求 LLM 输出 JSON → 下游 Code 节点解析
  • Vision 多模态：LLM 节点支持传入图片文件（需视觉模型）
  • reasoning_content：对推理模型，可获取完整思考链路
// 源码：LLM_OUTPUT_STRUCT // web/app/components/workflow/constants.ts export const LLM_OUTPUT_STRUCT: Var[] = [ { variable: 'text', type: VarType.string }, { variable: 'reasoning_content', type: VarType.string }, { variable: 'usage', type: VarType.object }, ]
避坑指南

LLM 节点 — 三大常见错误

❌ 变量引用格式错误

必须写 {{nodeId.fieldName}}，不是 {{nodeId.output}}。
字段名需与上游节点的 输出变量名 完全一致。

❌ 上下文窗口溢出

知识检索结果太长，超出模型 token 限制。
解决：限制 TopK、设置分数阈值、控制上下文长度。

❌ 忘记配置错误处理

LLM 调用失败默认终止整个工作流。
建议在节点设置中启用 "失败时继续"，配合 IF-ELSE 兜底。

📚 提示词模板示例

// System Prompt 你是一个专业的数据分析师。请分析以下数据： {{start.query}} 请从以下维度进行分析： 1. 数据趋势 2. 异常点 3. 改进建议 // 输出格式要求 请以 JSON 格式返回： { "trend": "...", "anomalies": [...], "suggestions": [...] }

✔ 变量引用格式正确: {{start.query}}
✔ 输出格式明确、可用于下游解析
✔ 提示词聚焦具体分析维度

AI/LLM #2

KnowledgeRetrieval — 知识库检索

从 Dify 知识库中检索与查询最相关的文档片段

3 种检索模式

混合检索（推荐）：关键词 + 语义向量双路召回后融合排序，兼顾精确匹配和语义匹配

语义检索：纯向量相似度，适合长文本、模糊问题

全文检索：纯关键词匹配，适合精确查询（编号/姓名/术语）

关键配置参数

参数推荐值说明
TopK3 - 5返回最相关的 K 个片段
分数阈值0.5 - 0.7低于此分数丢弃
Rerank可选对 TopK 结果再精排

输出结构 & 标准模式

{ result: [{ content: string, // 片段正文 title: string, // 所属文档标题 url: string, // 文档 URL icon: string, metadata: { dataset_id: string, dataset_name: string, document_name: string, segment_position: number, segment_word_count: number, score: number } }]}

标准 RAG 模式：

Start→ 知识检索→ LLM→ Answer

在 LLM 上下文配置中引入 {{知识检索节点.result}}

避坑指南

知识检索 — 4 个关键决策

❌ 不设分数阈值

低质量结果会污染 LLM 上下文，导致幻觉或答非所问。
✔ 设置 score >= 0.5 过滤噪音。

❌ TopK 太大

检索结果 + 提示词 + 回复会超出模型上下文窗口。
✔ TopK 3-5，配合 Rerank 精排。

❌ 只用语义检索查精确值

编号/代码/日期/人名需要精确命中。
✔ 精确查询用全文检索或混合检索。

✅ 最佳实践

1. 知识库分段控制在 500-1000 token
2. 启用混合检索 + Rerank
3. 在 LLM 提示词中标注引用来源
4. 分数阈值从 0.5 开始，逐步调优

流程控制 #1

IF-ELSE — 条件分支

IF / ELIF / ELSE 匹配链，支持 AND/OR 组合条件

支持的条件类型

条件说明示例
is / is not等于 / 不等于status is "paid"
contains包含子串query contains "退款"
starts_with以...开头code starts_with "ERR"
is_empty是否为空result is_empty
greater_than数值大于score > 0.8
in / not in集合包含city in ["北京","上海"]

条件组合：多个条件通过 AND（全部满足）或 OR（任一满足）组合。

意图路由模式

// 意图路由示例 IF sys.query contains "退款" → 退款处理分支 ELIF sys.query contains "退货" → 退货处理分支 ELIF sys.query contains "物流" → 物流查询分支 ELSE → 智能客服兜底

配合问题分类器的完整路由

Start→ 分类器→ IF-ELSE

class_label == "refund" → 退款处理
class_label == "inquiry" → 咨询处理
ELSE → 通用客服

避坑指南

IF-ELSE — 三大致命错误

⛔

分支逻辑不互斥

第一个 IF 条件太宽，导致后续分支永远不会执行。

修复：从最具体的条件开始，逐步放宽。

⛔

忘记 ELSE 兜底

没有匹配条件时不会报错，但工作流会静默跳过，导致下游节点收到空值。

修复：每个 IF-ELSE 必须有 ELSE。

⛔

深层嵌套 >3 层

画布混乱、难以调试、执行路径组合爆炸。

修复：超过 3 层嵌套用问题分类器扁平化。

数据处理 #1

Code — 代码执行节点

Python3 / JavaScript 沙箱执行，处理复杂数据转换

核心机制

语言：Python3 或 JavaScript (Node.js)

输入变量：声明引用，名称与 args.变量名 对应

main() 函数：返回 dict/object 成为下游可引用的输出字段

版本：取决于 Dify 沙箱环境中的 Python/Node 版本

典型场景

  • JSON 解析与结构化提取
  • 数组过滤、排序、聚合
  • 数据清洗与格式转换
  • 多源数据合并与计算

Python 完整示例

def main(args): # args 是输入变量 dict text = args.get('input_text', '') # 处理逻辑 word_count = len(text.split()) lines = text.split('\n') # 返回 dict — 成为下游可引用的输出 return { 'word_count': word_count, 'line_count': len(lines), 'summary': text[:200] + '...' if len(text) > 200 else text }
避坑指南

Code 节点 — 沙箱限制与常见错误

沙箱限制（必须了解）

🔒 默认无外部网络访问

🔒 无文件系统写权限（可读临时文件）

🔒 执行超时限制（不宜做耗时操作）

🔒 内存限制（大数据处理需分批）

// 源码：CodeLanguage 枚举 // api/core/workflow/nodes/code/entities.py class CodeLanguage: PYTHON3 = "python3" JAVASCRIPT = "javascript"

常见错误 & JSON 聚合示例

❌ 耗时操作超时 — 大数据拆成多个节点

❌ 返回不可序列化对象 — 只能返回 dict/list/str/int/float/bool/None

❌ 忘记声明输入变量 — 代码中 args['xxx'] 会为空

// JSON 解析与聚合 def main(args): import json items = args['items'] merged = [{'name': i['name'], 'score': float(i['score'])} for i in items] return { 'merged': merged, 'avg': sum(x['score'] for x in merged) / len(merged) }
数据处理 #2

HTTPRequest — HTTP 请求节点

在工作流中调用任何外部 REST API

配置参数

参数说明
MethodGET / POST / PUT / PATCH / DELETE / HEAD
URL支持变量插值 https://api.xxx.com/users/{{id}}
HeadersKey-Value，支持引用变量
BodyJSON / Form-Data / x-www-form-urlencoded / Raw Text / Binary
AuthNone / Bearer Token / Basic Auth / API Key
Timeout默认 10s，可自定义

输出结构

// web/app/components/workflow/constants.ts { body: string, // 响应体（文本） status_code: number, // HTTP 状态码 headers: object, // 响应头 Key-Value files: File[] // 响应文件列表 }

API Key 授权配置：支持放在 Header / Cookie / Query Parameter 三种位置，适合对接第三方 API。

模式 & 避坑

HTTPRequest — 常见模式与避坑

2 种典型模式

模式 1：Agent 调用外部数据源

Start→ HTTP→ Code→ LLM→ End

调企业 CRM API 查客户 → Code 格式化 → LLM 生成报告

模式 2：API 聚合器

Webhook→ HTTP A+ HTTP B→ Code→ End

两个独立 API 可并行调用，用 Code 节点合并结果

三大避坑

❌ 响应体编码问题
不是 UTF-8 编码时出现乱码。在 Code 节点中手动 .decode('gbk') 处理。

❌ 不处理 HTTP 错误码
4xx/5xx 导致节点失败，后续全部中断。启用"失败时继续"，用 IF-ELSE 检查 status_code。

❌ URL 参数未编码
中文/特殊字符需 URL encode。用 Code 节点 urllib.parse.quote() 预处理。

数据处理 #3

TemplateTransform — Jinja2 模板转换

将变量渲染为文本，最适合格式化检索结果 → LLM 上下文

常用 Jinja2 语法

{# 变量 #} {{ variable_name }} {# 过滤器 #} {{ text | upper }} {{ text | truncate(100) }} {{ items | length }} {{ date | default('未知') }} {# 循环 #} {% for item in items %} - {{ loop.index }}. {{ item.name }} {% endfor %} {# 条件 #} {% if score > 0.8 %} 匹配度高 {% elif score > 0.5 %} 匹配度中 {% else %} 匹配度低 {% endif %}

格式化检索结果为 LLM 上下文

以下是与 "{{ sys.query }}" 相关的知识库内容： {% for item in knowledge.result %} --- 文档：{{ item.title }} 来源：{{ item.url }} {{ item.content }} {% endfor %} 请基于以上信息回答用户问题。

避坑

❌ 模板语法错误 — Jinja2 报错不直观，先用简单模板测试

❌ 变量不存在 — 渲染为空白，用 | default() 防御

❌ 用模板做复杂逻辑 — 超过 10 行用 Code 节点

VariableAssigner — 变量赋值器

在工作流执行中写入/覆盖变量值。类似编程中的 = 赋值。

3 个典型场景

  1. 处理中间结果需要持久化到会话变量
  2. 聚合多个分支的结果到一个变量
  3. 对会话变量做增量写入（如累计计数）
// 赋值配置 变量名: user_topic 值: {{ llm_node.text }}

❌ 变量名与系统变量冲突
❌ 迭代内部写入的变量外部不可见

AI/LLM #3

QuestionClassifier — 问题分类器

使用 LLM 将用户输入分类到预设类别，输出类别标签

配置方式

// 分类定义 分类 1: name: "退款申请" label: "refund" 描述: "用户要求退款、取消订单" 分类 2: name: "商品咨询" label: "product_inquiry" 描述: "询问商品信息、规格、库存"

输出结构

{ "class_name": "退款申请", "class_label": "refund", "usage": { /* Token 用量 */ } }

配合 IF-ELSE 做意图路由

Start→ 问题分类器→ IF-ELSE
refund
→ 退款处理
inquiry
→ 咨询处理
ELSE
→ 通用客服

避坑

❌ 描述不精确 — LLM 容易误分类，描述要具体

❌ 类别过多 — 超过 10 个准确率下降，考虑两层分类

❌ 不用 IF-ELSE 处理未知类别 — ELSE 兜底非常重要

AI/LLM #4

ParameterExtractor — 参数提取器

从非结构化文本中提取结构化参数，适合 NL → 结构化数据

参数定义

属性说明
name参数名称
typetext / number / bool / select / array
description告诉 LLM 如何提取（关键！）
required是否必填

提示：可从已安装的插件工具中一键导入参数定义，保持工具调用和参数提取的一致性。

完整 YAML 配置示例

# 旅行规划助手 — 参数提取 参数: - name: city type: text description: "用户提到的城市名" required: true - name: budget type: number description: "预算金额，单位元" required: false - name: travel_dates type: array[text] description: "旅行日期列表" required: false

用户输入："帮我规划一下北京3天游，预算3000"
→ 提取：city="北京", budget=3000, travel_dates=[]

数据处理 #4

ListFilter — 列表过滤器

对数组变量进行过滤、排序、去重、限制操作

配置方式

配置项说明
变量引用数组类型变量
过滤条件字段 + 条件 + 值
排序按字段 ASC / DESC
限制取前 N 条
# YAML 配置示例 变量: {{迭代节点.output}} 过滤条件: - 字段: score 条件: greater_than 值: 0.8 排序: score DESC 限制: 10

支持的操作

过滤：基于条件筛选（is, contains, greater_than, is_empty 等）

排序：按指定字段升序/降序

去重：按字段去重

限制：取前 N 条

避坑

❌ 字段名不一致 — 区分大小写，要与数据中实际字段名完全匹配

❌ 空数组不设默认值 — 过滤后为空时下游节点可能出错

❌ 过滤后忘记限制数量 — 大数据集需要 limit 控制
