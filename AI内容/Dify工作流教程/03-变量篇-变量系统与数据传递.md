# 第三篇：变量篇 — 变量系统与数据传递

> 变量是工作流数据流转的血液。本篇深入讲解 Dify 变量系统的完整机制：变量怎么存、怎么引用、怎么转换，以及作用域和常见问题。

---

## 1. 变量池（VariablePool）是如何工作的？

### 1.1 本质：以选择器为 Key 的 KV 存储

Dify 工作流的所有变量存储在一个 `VariablePool` 中。每个变量通过一个**选择器（Selector）**唯一标识，格式为：

```
(节点ID, 字段名)
```

例如：
- `("17200001", "text")` → LLM 节点的 `text` 输出
- `("sys", "query")` → 系统变量 `query`
- `("17200003", "result")` → 知识检索节点的 `result` 输出

```python
# api/core/workflow/variable_pool_initializer.py
def add_variables_to_pool(variable_pool, variables):
    for variable in variables:
        variable_pool.add(variable.selector, variable)  # selector = (node_id, field)

def add_node_inputs_to_pool(variable_pool, *, node_id, inputs, aliases=()):
    for current_node_id in [node_id] + list(aliases):
        for key, value in inputs.items():
            variable_pool.add((current_node_id, key), value)
```

### 1.2 变量的生命周期

```
┌─────────────┐     ┌─────────────┐     ┌─────────────┐
│ 工作流启动    │ →   │ 节点依次执行  │ →   │ 工作流结束    │
│ 注入系统变量  │     │ 每次输出写入   │     │ 变量池销毁    │
│ 初始化变量池  │     │ 变量池        │     │              │
└─────────────┘     └─────────────┘     └─────────────┘
```

每个节点的输出在**该节点执行完成时**立即写入变量池，后续节点可以引用。

## 2. 四类变量及其前缀

Dify 用不同的 `node_id` 前缀区分变量来源：

```python
# api/core/workflow/variable_prefixes.py
SYSTEM_VARIABLE_NODE_ID       = "sys"           # sys.xxx
ENVIRONMENT_VARIABLE_NODE_ID  = "env"           # env.xxx
CONVERSATION_VARIABLE_NODE_ID = "conversation"  # conversation.xxx
RAG_PIPELINE_VARIABLE_NODE_ID = "rag_pipeline"  # rag_pipeline.xxx
```

### 2.1 系统变量（sys.*）

自动注入，无需手动定义：

```python
# api/core/workflow/system_variables.py
class SystemVariableKey(StrEnum):
    QUERY                  "query"           # 用户输入文本
    FILES                  "files"           # 用户上传的文件
    USER_ID                "user_id"         # 当前用户 ID
    APP_ID                 "app_id"          # 应用 ID
    WORKFLOW_ID            "workflow_id"     # 工作流 ID
    WORKFLOW_EXECUTION_ID  "workflow_run_id" # 本次运行唯一 ID
    CONVERSATION_ID        "conversation_id" # 对话 ID（Chat 模式）
    DIALOGUE_COUNT         "dialogue_count"  # 对话轮次（Chat 模式）
    TIMESTAMP              "timestamp"       # 触发时间戳（Workflow 模式）
```

在前端 UI 中的引用方式：
```
sys.query
sys.user_id
sys.files
```

系统变量在**每个 Chat 模式**下额外追加：
```typescript
// web/app/components/workflow/constants.ts
{ variable: 'sys.dialogue_count', type: VarType.number },
{ variable: 'sys.conversation_id', type: VarType.string },
```

### 2.2 环境变量（env.*）

在 Dify 应用设置 → 环境变量中配置。适合存储 API Key、配置项等不硬编码的值。

```
env.API_KEY       # 引用环境变量 API_KEY
env.BASE_URL      # 引用环境变量 BASE_URL
```

### 2.3 对话变量（conversation.*）

仅在 Chat 模式中使用，跨对话轮次持久化。适合存储用户偏好、上下文等。

### 2.4 节点输出变量

格式：`{{节点ID.字段名}}`

在 UI 中通过变量选择器点选，自动生成引用路径。

## 3. 核心节点输出结构速查

每个节点执行后输出的字段是固定的。以下是常用节点的输出结构（源码 `constants.ts`）：

### LLM
```typescript
{ text: string }                    // 生成的文本
{ reasoning_content: string }       // 推理过程（思考链）
{ usage: {                          // Token 用量
    prompt_tokens: number,
    completion_tokens: number,
    total_tokens: number
  }
}
```

### 知识检索
```typescript
{ result: [{                        // 检索到的文档列表
    content: string,                // 文档片段内容
    title: string,                  // 文档标题
    url: string,                    // 文档链接
    icon: string,                   // Favicon
    metadata: { ... }               // 详细元数据
  }]
}
```

### HTTP 请求
```typescript
{ body: string }                    // 响应体
{ status_code: number }             // HTTP 状态码
{ headers: object }                 // 响应头
{ files: File[] }                   // 下载的文件
```

### Code
由 `main()` 函数返回的 dict/object 中的每个 key 变为一个输出字段。不固定，看你 return 了什么。

### 问题分类器
```typescript
{ class_name: string }              // 分类名称
{ class_label: string }             // 分类标签
{ usage: object }                   // Token 用量
```

### 参数提取器
由定义的参数列表决定，每个参数名成为一个输出字段。

### Agent
```typescript
{ text: string }                    // Agent 最终输出文本
{ files: File[] }                   // 输出文件
{ json: object }                    // 结构化输出
```

## 4. 变量的读写操作

### 4.1 读：模板中引用变量

在 LLM 提示词、HTTP URL、模板转换等处，通过选择器读取变量：

```
格式：{{节点ID.字段名}}

# 简单读取
{{llm.text}}
{{knowledge_retrieval.result}}

# 系统变量
{{sys.query}}
{{sys.user_id}}

# 环境变量
{{env.API_KEY}}
```

### 4.2 写：变量赋值器

`VariableAssigner` 节点可以在运行时写入/覆盖变量。相当于代码中的 `=`：

```yaml
# 将 LLM 的输出赋值给变量 processed_text
变量: processed_text
值: {{llm_node.text}}
```

**覆盖语义**：如果变量 `processed_text` 已存在，赋值节点会**覆盖**它。后续节点看到的是新值。

### 4.3 聚合：变量聚合器

`VariableAggregator` 将多个上游输出**收拢成数组**。本质上是收集分支结果：

```yaml
聚合变量: all_results
输出:
  - {{branch_a.result}}
  - {{branch_b.result}}
  - {{branch_c.result}}

# 结果：all_results = [branch_a.result, branch_b.result, branch_c.result]
```

## 5. 变量作用域 — 迭代和循环的隔离

### 5.1 子作用域创建

迭代（Iteration）和循环（Loop）节点内部是一个**子工作流**，有独立的变量作用域：

```
┌────────────────────────────────┐
│ 主工作流作用域                   │
│ 变量: sys.xxx, env.xxx, ...    │
│                                 │
│  ┌─────────────────────────┐   │
│  │ 迭代/循环子作用域         │   │
│  │ 内部变量对外部不可见      │   │
│  └─────────────────────────┘   │
│                                 │
└────────────────────────────────┘
```

### 5.2 典型问题

❌ **问题**：在迭代内部写入的变量，外部尝试引用 → 空值。

```yaml
# 错误示范
[Start] → [Iteration]
            └─ [VariableAssigner: score = 100]
         → [LLM: 尝试引用 {{score}}]  ← ❌ 引用不到！score 在迭代内部
```

✅ **解决方案**：迭代/循环的输出字段是唯一对外暴露的数据通道。如果需要内部变量，走输出。

### 5.3 迭代/循环的特殊变量

- **迭代**：每次迭代可用 `{{迭代节点.item}}` 获取当前元素
- **循环**：每次循环可用 `{{循环节点.index}}` 获取当前循环索引

## 6. 变量类型系统

### 6.1 基础类型

| 类型 | 说明 | 示例 |
|------|------|------|
| `string` | 文本 | `"hello"` |
| `number` | 数值 | `42`, `3.14` |
| `boolean` | 布尔 | `true`, `false` |
| `object` | JSON 对象 | `{"key": "value"}` |
| `array[string]` | 字符串数组 | `["a", "b"]` |
| `array[number]` | 数值数组 | `[1, 2, 3]` |
| `array[object]` | 对象数组 | `[{}, {}]` |
| `array[file]` | 文件数组 | 上传的文件 |

### 6.2 文件的子属性

文件类型变量有子属性：

```typescript
// web/app/components/workflow/nodes/constants.ts
file.type              // image / document / audio / video
file.size              // 字节数
file.name              // 文件名
file.url               // 文件 URL
file.extension         // 扩展名
file.mime_type         // MIME 类型
file.transfer_method   // local_file / remote_url
```

引用方式：`{{file_var.name}}`、`{{file_var.size}}`

### 6.3 类型不匹配

当节点期望 `string` 但你传了 `object`：

```
IF-ELSE 条件: sys.query is "退款"
```
这里 `sys.query` 是文本，`"退款"` 也是文本 → ✅ 匹配

```
IF-ELSE 条件: llm.usage > 50
```
`llm.usage` 是 object（含 prompt_tokens 等字段），不能直接和数值比较 → ❌ 类型不匹配

**解决**：用 Code 节点提取需要的字段 → `llm.usage.total_tokens` 输出为 number。

## 7. 常见变量传递模式

### 模式 1：直线串联

```
[Start] → [LLM 分析] → [Code 格式化] → [End]
          ↓ 输出 text   ↓ 引用 llm.text
```

最简单、最可靠。每个节点引用紧邻上游的输出。

### 模式 2：知识增强

```
[Start] → [知识检索] → [模板转换] → [LLM] → [End]
          ↓ result                ↓ 注入检索结果
```

模板转换节点拼接检索结果为 LLM 上下文。

### 模式 3：分支聚合

```
               → [分支A: LLM-GPT] → 
[Start] → [IF] → [分支B: LLM-Claude] → [聚合器: all_results] → [End]
               → [分支C: 规则处理] →
```

聚合器收集多路的输出为数组。

### 模式 4：数据管线

```
[触发] → [HTTP: 拉数据] → [Code: 清洗] → [LLM: 分析] → [Code: 格式化] → [HTTP: 写回] → [End]
```

每个节点处理上一个的输出，形成数据管道。

## 8. 常见变量问题排查

### 问题 1：变量选择器里找不到上游节点

**原因**：没有边连接。

**修复**：确保两个节点之间有箭头（边）连接。没有边 = 引擎认为它们没有依赖关系。

### 问题 2：引用值是空的

**检查清单**：
1. 上游节点是否执行了？（看运行日志）
2. 引用的字段名是否正确？（区分大小写）
3. 是否在迭代/循环内部定义的变量？（作用域隔离）
4. 上游节点是否设置了"失败时继续"但实际失败了？

### 问题 3：模板渲染结果不对

```jinja2
# ❌ 错误 — result 是 array[object]，不能直接当字符串拼接
{{知识检索.result}}

# ✅ 正确 — 遍历数组取字段
{% for item in 知识检索.result %}
{{ item.content }}
{% endfor %}
```

### 问题 4：赋值器写入变量后仍为空

检查：
1. 赋值器的执行顺序 — 是否在引用它的节点**之前**执行？
2. 是否被 IF-ELSE 跳过？（如果赋值器在某个分支里，但走了另一个分支）
3. 变量名没有冲突。
