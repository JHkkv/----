## 1. 触发器（Trigger）

触发器让工作流自动运行，不需要手动或 API 调用。Dify 支持 3 种触发器类型：

```python
# api/core/trigger/constants.py
TRIGGER_WEBHOOK_NODE_TYPE  = "trigger-webhook"   # 配置在 api/core/workflow/nodes/trigger_webhook/
TRIGGER_SCHEDULE_NODE_TYPE = "trigger-schedule"  # 配置在 api/core/workflow/nodes/trigger_schedule/
TRIGGER_PLUGIN_NODE_TYPE   = "trigger-plugin"    # 配置在 api/core/workflow/nodes/trigger_plugin/
```

### 1.1 Webhook 触发器

**触发方式**：向一个特殊 URL 发 HTTP 请求 → 工作流启动。

**配置**：
1. 在工作流开头添加"Webhook 触发器"节点
2. Dify 自动生成一个 Webhook URL
3. 外部系统向该 URL 发请求即可触发

**Payload 访问**：
```yaml
# POST /webhook/xxx 发送的 JSON body
{
  "event": "order_created",
  "data": { "order_id": "12345" }
}

# 工作流中引用：
{{trigger_webhook.event}}
{{trigger_webhook.data.order_id}}
```

**安全建议**：
- ✅ 在 Webhook URL 中带随机 token（如 `/webhook/xxx?token=random123`）
- ✅ 在 HTTP 请求节点中验证请求签名
- ✅ 配置 IP 白名单（在 Dify 部署层）

### 1.2 定时触发器（Schedule）

**触发方式**：按 Cron 表达式自动触发。

**Cron 语法**（5 字段）：
```
分钟 小时 日 月 星期

# 常见配置：
0 9 * * *         # 每天上午 9:00
0 */2 * * *       # 每 2 小时
30 8 * * 1-5      # 工作日 8:30
0 0 1 * *         # 每月 1 号 0:00
0 9 * * 1         # 每周一 9:00
```

**输入变量**：可通过输入变量传递触发上下文，如触发时间、触发类型等。

**前端面板**：
```
web/app/components/workflow/nodes/trigger-schedule/
├── default.ts          # 默认配置
├── panel.tsx           # 配置面板
└── components/
    └── next-execution-times.tsx  # 下次执行时间预览
```

### 1.3 插件触发器

**触发方式**：由已安装的第三方插件触发。例如：
- GitHub 有新的 Issue → 触发
- 邮件收到新消息 → 触发
- 数据库有新记录 → 触发

配置方式取决于具体插件，Dify 提供统一的触发器插件接口。

### 1.4 DataSource — 数据源起始节点

与触发器不同，DataSource 是在 API 调用时**主动拉取**外部数据作为输入：

```python
# api/core/workflow/nodes/datasource/
# 支持从外部数据源加载数据到工作流
```

`DataSource` 在触发器列表里单独列举，但它的运作方式是在触发节点中指定"数据来源"字段，引擎执行时会先去拉数据再注入到工作流的输入。

## 2. HumanInput — 人工介入（HITL）

### 2.1 什么是 HITL？

Human-In-The-Loop：工作流运行到某个节点时**暂停**，等待人类做出决策后再继续。

```python
# api/core/workflow/nodes/human_input/
# entities.py     → HumanInputNodeData（表单定义、触发条件）
# boundary.py     → 工作流暂停 / 恢复边界
# callback.py     → DifyHITLCallback
```

### 2.2 配置步骤

**第 1 步：添加 HumanInput 节点**

在工作流中插入"人工输入"节点。

**第 2 步：设计表单**

定义人工需要填写的内容：

| 字段 | 类型 | 说明 |
|------|------|------|
| 审批意见 | 下拉 | 通过 / 拒绝 / 需修改 |
| 修改建议 | 段落 | 具体的修改内容 |
| 优先级 | 下拉 | 高 / 中 / 低 |

**第 3 步：配置通知**

- **站内通知**：Dify 工作区内的用户看到待处理任务
- **邮件通知**：通过 SMTP 发送到指定邮箱
- **API 回调**：向外部系统发通知（自定义 Webhook）

**第 4 步：下游节点引用人工输入**

```
{{human_input_node.审批意见}}
{{human_input_node.修改建议}}
```

### 2.3 完整 HITL 示例：内容审核工作流

```
[Start:用户提交文章] → [LLM:AI初审(敏感性/合规性检查)] → [HumanInput:人工复审]
                                                              ├─ 通过 → [End:发布]
                                                              └─ 拒绝 → [End:返回修改意见]
```

**LLM 初审的 System Prompt**：
```
你是内容审核助手。检查以下文章是否存在：
1. 政治敏感内容
2. 色情暴力内容
3. 虚假信息
4. 侵犯隐私内容

文章内容：
{{sys.query}}

输出 JSON：
{
  "risk_level": "low" | "medium" | "high",
  "issues": ["具体问题1", "具体问题2"],
  "recommendation": "建议通过" | "建议人工复审" | "建议拒绝"
}
```

**HumanInput 表单**：
- 显示：`{{llm初审.issues}}`（AI 发现的问题）
- 字段 1：审核决定（通过/拒绝/修改后重审）
- 字段 2：审核意见（段落）

**条件路由**：
- 审核决定 == "通过" → End（发布文章）
- 审核决定 == "拒绝" → End（返回拒绝原因）
- 审核决定 == "修改后重审" → 回到 Start（重新提交）

### 2.4 工作流暂停/恢复机制

```python
# api/core/workflow/nodes/human_input/boundary.py
# HumanInput 节点执行时：
# 1. 保存当前 GraphRuntimeState（变量池、执行位置）
# 2. 创建 PauseState 持久化记录
# 3. 发出暂停事件 → 停止引擎
# 
# 人工操作完成后：
# 1. 加载 PauseState
# 2. 将填写的表单数据注入变量池
# 3. 从暂停点恢复引擎执行
```

### 2.5 避坑

- ❌ HumanInput 节点设置超时太短（人工可能需要几小时甚至几天）
- ❌ 没有设计超时后的默认行为（超时后自动通过？自动拒绝？需提前配置）
- ❌ 表单字段太多（人工不愿意填，控制在 5 个以内）

## 3. 迭代（Iteration）与循环（Loop）

### 3.1 迭代 — 并行处理数组

**适用场景**：对一个数组的每个元素做同样的处理。

```
[Start:文章列表] → [Iteration]
                      └─ [LLM:总结单篇文章] → [End-Iteration:收集所有总结]
                   → [聚合器:合并总结]
                   → [LLM:生成综述] → [End]
```

**关键配置**：
- **输入变量**：选择数组类型变量（如 `{{http_请求.body.items}}`）
- **并行度**：同时处理的元素数量（最大并行度受配置限制）
- **输出变量**：迭代完成后输出结果数组

**在迭代内部可用**：
```jinja2
{{iteration.item}}        # 当前元素
{{iteration.index}}       # 当前索引（从 0 开始）
{{iteration.output}}      # 所有迭代的输出数组
```

**前端实现**：
```typescript
// web/app/components/workflow/nodes/iteration/
// default.ts     → 默认配置
// types.ts       → 迭代参数类型
// add-block.tsx  → 在迭代内添加节点
```

### 3.2 循环 — 条件循环

**适用场景**：根据条件重复执行，直到满足退出条件。

```
[Start] → [LoopStart]
            ├─ [LLM:处理一次]
            ├─ [Code:检查是否继续]
            └─ [LoopEnd]
          → [聚合] → [End]
```

**关键配置**：
- **循环条件**：定义何时退出循环
- **最大循环次数**：防止无限循环（硬限制）
- **循环变量**：可在循环中访问循环索引和状态

**循环内可用**：
```jinja2
{{loop.index}}            # 当前循环轮次
{{loop.item}}             # 当前数据（如传入数组）
{{loop.output}}           # 所有循环输出
```

### 3.3 迭代 vs 循环 — 如何选择

| 特性 | 迭代 | 循环 |
|------|------|------|
| 输入 | 数组 | 任意条件 |
| 并行 | 支持 | 串行 |
| 退出 | 数组走完 | 条件满足 |
| 适用 | "对每个 X 做 Y" | "重复做直到 Z" |
| 顺序保证 | 不保证（并行时） | 严格按顺序 |

**选择规则**：
- 你知道有多少次（有数组）→ 迭代
- 你不知道多少次（有条件）→ 循环

### 3.4 避坑

- ❌ 迭代/循环内定义了外部需要的变量 → 作用域隔离，外面看不到
- ❌ 循环没有设置最大次数 → 死循环风险
- ❌ 迭代并行度设太大 → 超出 LLM API 并发限制
- ❌ 在迭代内部做昂贵的 LLM 调用 × 100 → 成本爆炸

## 4. 错误处理策略

### 4.1 三种错误处理模式

Dify 提供 3 种错误处理策略（定义在 `ErrorHandleMode`）：

```typescript
// web/app/components/workflow/types.ts
enum ErrorHandleMode {
  Terminated = 'terminated',                // 终止工作流（默认）
  ContinueOnError = 'continue-on-error',    // 失败时继续
  RemoveAbnormalOutput = 'remove-abnormal-output'  // 移除异常输出后继续
}
```

#### Terminated（终止）
- 默认策略
- 节点失败 → 工作流立即终止
- 适合：关键节点（数据验证、安全检查）

#### ContinueOnError（继续）
- 节点失败 → 跳过该节点，继续执行
- 下游节点引用失败节点的输出 → 得到空值
- 适合：非关键的外部 API 调用、可选的数据增强

#### RemoveAbnormalOutput（移除异常输出）
- 节点失败 → 移除该节点的输出，继续执行
- 适合：并行分支中某个分支失败不影响整体

### 4.2 前端配置

每个节点的错误处理配置在面板中设置：

```typescript
// web/app/components/workflow/nodes/_base/components/error-handle/
// error-handle-on-node.tsx   → 节点上的错误状态显示
// error-handle-on-panel.tsx  → 面板中的错误策略配置
// types.ts                   → ErrorHandleTypeEnum
```

### 4.3 错误处理最佳实践

```yaml
# 保守策略（生产环境推荐）
LLM 节点:    Terminated       # 核心推理环节
HTTP 节点:   ContinueOnError  # 外部依赖可能不稳定
Tool 节点:   ContinueOnError  # 第三方工具可能出错
Code 节点:   Terminated       # 代码逻辑错误应暴露
Agent 节点:  ContinueOnError  # Agent 是多步的，单步失败不应终止
```

### 4.4 重试机制

除了错误处理模式，Dify 还支持节点级别的重试配置：

```typescript
// web/app/components/workflow/nodes/_base/components/retry/
// retry-on-node.tsx  → 节点上的重试按钮
// retry-on-panel.tsx → 面板中的重试配置
```

**可配置项**：
- 最大重试次数
- 重试间隔
- 重试策略（固定间隔 / 指数退避）

### 4.5 IF-ELSE 错误分支

在关键节点后加 IF-ELSE 判断结果：

```
[HTTP: 调外部 API]
  ↓
[IF: status_code == 200]
  ├─ Yes → [正常处理]
  └─ No  → [Code: 从缓存读]  或  [LLM: 生成兜底回复]
```

## 5. Agent 节点

### 5.1 Agent v2 架构

Agent v2 是当前 Dify 的主力 Agent 实现：

```python
# api/core/workflow/nodes/agent_v2/
# agent_node.py              ← DifyAgentNode 主体
# entities.py               ← DifyAgentNodeData（节点配置数据模型）
# dify_tools_builder.py     ← 工具构建器（核心插件/工具）
# runtime_request_builder.py ← Agent 运行时请求构建
# output_adapter.py         ← Agent 输出适配
# validators.py             ← 发布前校验
# ask_human_hitl.py         ← Agent 内嵌 HumanInput 支持
```

### 5.2 Agent 工具绑定

Agent 可以调用以下类型的工具：

**A. 插件工具**
```python
# dify_tools_builder.py
DifyPluginToolsLayerConfig   ← 已安装的插件
  - Google Search, DALL·E, 代码解释器等
```

**B. 内置工具**
```python
DifyCoreToolsLayerConfig     ← Dify 内置
  - 知识库检索（内嵌在 Agent 中）
  - 其他内置能力
```

**C. 工作流作为工具**
```python
WorkflowToolProviderController ← 将子工作流注册为工具
```

### 5.3 Agent 配置最佳实践

**System Prompt 设计**：
```
你是 [角色]。你可以使用以下工具来完成用户的任务。

可用工具：
[列出工具及用途]

行为规则：
1. 遇到 [场景A] 时 → 使用 [工具X]
2. 遇到 [场景B] 时 → 使用 [工具Y]
3. 如果所有工具都不适用 → 直接基于知识回答
4. 每次回复前检查是否需要调用工具

输出格式：
- 工具调用：返回工具名称和参数
- 最终回复：用 markdown 格式
```

**工具选择建议**：
- ✅ 每个工具有清晰的使用场景描述
- ✅ 工具数量控制在 3-8 个（太多 Agent 选不好）
- ✅ 给工具起描述性的名字（`search_customer_by_email` > `tool_1`）
- ✅ 工具参数描述精确（"customer email address" > "input"）

## 6. 高级数据流模式

### 6.1 知识库多路召回

```
                        ┌→ [知识检索A: 语义检索]
[Start:用户问题] →         → [知识检索B: 全文检索] 
                        └→ [知识检索C: 混合检索，不同知识库]
                                                → [Code: RRF融合排序] → [LLM]
```

RRF（Reciprocal Rank Fusion）融合算法：
```python
def main(args):
    results_a = args.get('retrieval_a_result', [])
    results_b = args.get('retrieval_b_result', [])
    results_c = args.get('retrieval_c_result', [])
    
    # 计算每个文档的 RRF 分数
    scores = {}
    k = 60  # RRF 常数
    
    for rank, doc in enumerate(results_a):
        doc_id = doc.get('metadata', {}).get('document_id', '')
        scores[doc_id] = scores.get(doc_id, 0) + 1 / (k + rank + 1)
    for rank, doc in enumerate(results_b):
        doc_id = doc.get('metadata', {}).get('document_id', '')
        scores[doc_id] = scores.get(doc_id, 0) + 1 / (k + rank + 1)
    for rank, doc in enumerate(results_c):
        doc_id = doc.get('metadata', {}).get('document_id', '')
        scores[doc_id] = scores.get(doc_id, 0) + 1 / (k + rank + 1)
    
    # 按分数排序，去重
    all_docs = {doc['metadata']['document_id']: doc 
                for doc_list in [results_a, results_b, results_c] 
                for doc in doc_list}
    
    sorted_docs = sorted(
        all_docs.values(),
        key=lambda d: scores.get(d['metadata']['document_id'], 0),
        reverse=True
    )[:10]
    
    return {'merged_results': sorted_docs}
```

### 6.2 条件发布管道

```
[LLM:生成内容] → [IF: 质量检查]
                   ├─ score > 0.8 → [直接发布]
                   ├─ score > 0.5 → [LLM:优化] → [发布]
                   └─ score < 0.5 → [HumanInput:人工改写] → [发布]
```

### 6.3 链式 Agent

```
[Agent A: 研究助手] → [Agent B: 分析助手] → [Agent C: 写作助手]
   搜索 + 收集信息        分析 + 发现洞察        撰写 + 格式化
```

每个 Agent 是独立的 Agent v2 节点，输出文本传给下一个 Agent 作为输入。

## 7. 性能调优清单

### LLM 成本控制
- [ ] 问题分类器用便宜的模型（Haiku / GPT-4o-mini）
- [ ] 只在"主 LLM"节点用贵的模型（Opus / GPT-4o）
- [ ] 设置 LLM 的 `max_tokens` 限制
- [ ] 用缓存（知识库检索的 TopK 减小到 3-5）

### 工作流结构
- [ ] 并行分支中，最长路径不在关键路径上
- [ ] 迭代内部避免深度嵌套（迭代套迭代套 LLM）
- [ ] 大文件处理在独立的分支中异步进行

### 错误恢复
- [ ] HTTP/Tool 节点启用了重试
- [ ] Agent 节点启用了 ContinueOnError
- [ ] 关键路径有兜底逻辑
- [ ] HumanInput 设置了合理的超时
